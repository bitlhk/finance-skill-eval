# 开发测试案例设计

先阅读任务目标、Skill、相关工具或工程及已有开发案例，分析用户实际要完成的任务、业务规则、输入输出、关键步骤、工具调用及其状态变化。区分原有行为、用户期望和可运行条件；原工程结果只能作为对照证据，不能自动当作标准答案。

根据实际业务选择有区分度的场景。可以考虑正常路径、参数和状态边界、信息不足时的澄清、多步和多轮任务、权限及预期拒绝、依赖故障与恢复、跨工具协作，以及写操作的前后状态；不适用的类型无需凑数。结合业务风险和用户目标优先覆盖关键场景，说明每类场景为什么需要测试、有哪些依赖和未覆盖范围；不要声称有限案例覆盖全部业务。

优先使用用户或测试环境已提供的事实、可用标识和期望；缺少事实时使用可验证的行为要求并明确待补数据，不编造业务结果、标准答案或真实用户。对每项要求考虑应依据最终回答、工具过程、业务状态还是原工程对照来判断，必要时结合规则、脚本或模型；无法判断时说明需要的证据。涉及写操作时标明需要隔离数据和状态恢复，不替用户确认只读。

使用 propose_development_cases 提出开发案例供用户审阅和加入测试集草稿；单次建议数量受工具限制，必要时可以分批提出并说明各批覆盖，不要仅为凑数量而重复案例。不要改已有判据、创建留出集或将建议当作已通过的评测。用户可继续编辑案例、选择规则、脚本或模型评判，再保存和运行。
