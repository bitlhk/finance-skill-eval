version: 1
---

围绕用户选择的业务范围，先读取相关 Skill、源码和现有运行方式，理解共享依赖、实际行为与运行要求。完整 Agent 工程可能没有独立 Skill 文件；以实际代码和用户目标为准，不凭文件位置或名称猜测资产。需要改变用户确定的范围或业务规则时先沟通；无关能力不自动升级为本次验收要求。

原始材料是基线，只修改候选工作区。保留选定范围内应保持的业务语义、错误处理、必要资源和接口，以及 Skill 入口的业务身份；修复元数据时避免无依据地改名或改变含义。存在已知缺陷时区分原有行为、期望行为和证据。用户要求先建立失败基线时，先记录真实结果，再进入修复与优化。不要编造业务数据、测试结果、调度配置或固定答案。

依据实际用途选择工具形态：需要共享发现、远程接入与治理的能力可选 MCP；人、Agent 和自动化共用且需要组合调用的命令可选 CLI；局部胶水、数据处理或一次性任务可选脚本。CLI 与脚本按使用场景提供非交互运行、结构化输出、明确错误和超时等能力。结合复用范围、运维成本、安全边界和已有能力说明取舍，不按工具来源或文件类型机械分类。Runtime 缺客户端时，将客户端支持列为运行环境改造要求，不仅因此降低工具方案。`read_agent_skill` 等运行时自带的 Skill 加载能力不应作为待迁移的业务工具。

业务参数、调用者身份、服务连接认证和下游凭据分别分析，沿用用户现有身份机制；不把框架对象混入可复用的业务工具接口，也不自行编造鉴权要求或密钥。Skill 文档说明何时使用能力及业务约束，安装、配置和服务运行方式放在适合的工程文档中。不要把运行环境、虚拟环境或依赖目录作为交付物。

原工程通过登录态或请求 Header 取得调用者身份时，迁移后保留请求级传递：由可信 Runtime 上下文注入，工具从本次请求读取，再传给业务服务。服务地址、服务密钥等部署配置可以来自环境变量；不能把逐请求身份改成 MCP 进程里的固定用户，也不能放进模型业务参数或让用户在聊天中补报。身份缺失时报告接入配置错误，不回退到默认用户。复用已有 runtimeToolConfig 的 contextBindings/authProvider；按需阅读 task/platform/service-templates.md 的请求上下文说明。验证同一服务下不同用户的交叉、并发调用和越权失败，单用户实例通过不等于请求隔离通过。

按需使用已有工具检查代码、运行工程测试和验证实际交付入口；效果评测复用用户选择的测试集、运行环境和判定方式。分别说明已验证内容、无法验证的条件和遗留问题。缺少凭据、运行环境或安全样例时如实记录，不把未执行或失败的检查称为通过。

涉及工具交付时，运行入口的接入要求和可选骨架在工作区 `task/platform/service-templates.md`，形态取舍参考 `task/platform/tool-form-selection.md`。按需用 read_file 阅读；这些是平台已有运行契约，不能凭框架默认值猜测传输方式或启动参数。

`task/manifest.json` 提供本次目标、材料与可用约束；其中企业标准和选型指导按任务适用范围使用。旧阶段入口如要求填写计划或缺失项，只把确实阻止工作且必须由用户补充的信息列为缺失，不把尚未请求或不适用的文件当作阻塞项。
