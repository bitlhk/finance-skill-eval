# 跨部署复用验收

复用验收继续使用现有冻结测试集、Runtime 执行和业务 Judge；不引入另一套执行器。

## 选择与冻结

主 Runtime 与模型保持原入口。可额外选择最多三份已准入部署及各自模型。
`POST /api/migrations/:id/reuse-acceptance/plan` 接收可选 `additionalRuntimes`：

```json
{"environmentId":"primary","modelId":"model-a","additionalRuntimes":[{"environmentId":"other","modelId":"model-b"}]}
```

每个 `groups[]` 可使用 `runtime: {environmentId, modelId}`；省略时使用主部署。
所有指定目标必须来自用户选择。必须执行主部署和全部附加部署，未覆盖时不能确认。
各目标的环境、能力、模型、部署 ID、交付准入摘要及端点摘要随计划冻结；公开计划不包含凭据或端点原文。
变更任何目标的准入、能力或连接后，旧确认和旧结果失效，执行中的任务也停止形成通过结论。

## 准入与证据

跨部署要求各目标有有效 Builder 交付及 Eval 生命周期准入记录，具有不同部署 ID、Launcher 和端点。
同部署重复登记、新实例及改名均不能替代新部署。部署可以使用同一不可变 Runtime 产物，
但必须独立部署与执行；优化重建另有“产物必须改变”的要求，两者不能混为一谈。

候选原生工具绑定和能力要求仍按每个目标独立验证。只有主部署的能力确认不能授权其他部署；
额外目标必须已有当前迁移需求对应的独立准入，不能在验收时临时伪造交付或扩大权限。

运行结果保留实际分组 job；check 层获得对应已核实的部署身份与交付摘要、实例、会话和工作区证据。
case Judge 仍只检查本案例实际可见业务事实，不能要求其比较不同部署或推断隐藏状态。
用户仍须确认计划；没有模型判定或原承诺未覆盖时不计为通过。

## 验收状态

单元测试覆盖真实目标路由、别名拒绝、缺少/过期/变化的准入、未选择或未执行目标及确认失效。
这些故障注入测试不等于真实模型 UI 验收，也不证明 Harness 重建或八个 Skill 均已验收。
真实验收须另外记录固定三仓版本、部署实际创建与生命周期准入、UI 选择/确认、各组执行和清理。
