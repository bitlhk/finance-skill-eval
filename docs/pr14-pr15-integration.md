# PR14、PR15 与可复用迁移分支的融合

## 业务边界

- **独立 Skill 对比评测**：输入已可使用的 Skill 资产和兼容 Runtime，不隐式触发迁移或 Builder。一个 Skill 在两个 Runtime 上执行时，两侧独立验收，不制造相对胜负；不同 Skill 的对比仍保留原有比较方式。
- **Skill 迁移**：确认可复用方案，保留业务语义，将可迁移实现转成 MCP/Script；确实无法由可复用工具实现的宿主能力才进入 Runtime 能力核对或 Builder 交付。
- **迁移后的验收**：业务效果、复用设计审查和复用验收缺一不可。跨 Runtime 对照是独立证据，不替代业务验收，也不直接成为可交付结论。

两条流程复用资产、冻结案例、执行绑定、Judge、观测及回收能力，不共用迁移状态机，也不改写已有报告。迁移候选进入资产库后，可以明确发起一项独立评测。

## 吸收内容

PR14 的双 Runtime 独立目标评估、工具安装范围与兼容性、案例文件读取回执、事实来源、账户工作区隔离、环境归档、版本选择和限流能力；PR15 的取消收尾回执、刷新后保留终态、按原配置新建重试及历史失败保留。

当前分支的方案确认、源码迁移、MCP/Script 打包、现有 Runtime 合同复用、多轮工作区输入、复用验收、目标驱动改进和方案版本留存均保留。未用 PR 的迁移页面替换这些流程；交付导入和多端交付历史已融入现有适配页面。

## 整合修正

- 报告与执行共用交付判定：需求与交付摘要、请求标识、登记记录、有效期和生命周期验收必须对应；每端单独检查，不借用另一端交付。
- 通用迁移依赖 Launcher 能力合同，不锁死 OpenJiuwen/AgentScope 或某个 Java 版本。旧 generic 注册需要在线身份声明；演示资料的版本约束不是产品约束。
- 独立跨 Runtime 对照遇到某端执行失败，保留首错并将该端后续案例标为未执行。迁移运行保留原有行为：先回收失败实例，再为下一案例创建新实例，不重放失败案例。
- 多实例回收记录逐实例保存；HTTP 成功、取消请求或空 DELETE 响应均不能推断资源已释放。只留有界的结构化回执，不复制原始错误和凭据。
- 共享工具声明解析下沉至 shared 层；迁移交付使用统一完整资产打包器，保留真实 Skill 入口及二进制文件。
- 跨 Runtime 的模型按 `upstreamModelId` 匹配，分别保留 Launcher 本地 ID；不能以同名 alias 推断同模型，也不能因不同 alias 排除同模型。后端独立核验实际声明。
- Skill 版本选择、下拉值与执行绑定统一使用版本和产物摘要；同版本不同内容单独显示，不能让已装配的 Skill 误显示为未加载。
- 案例文件读取回执与现有输入摘要证据并存，不把私有文件正文送给 Judge，不将读取回执等同于业务通过。
- Windows 固定样例使用 LF 字节，部署脚本使用可移植路径；子进程回收等待关闭且不静默吞掉未退出状态。

## Judge 版本

新增分轮查询、工作区摘要与案例读取证据后，新运行使用 `fact-provenance-v3`。旧 v2 记录不重新计分。事实归属冻结脚本显式固定 v3 的 LF 源码摘要，输出新实验批次，不能覆盖原批次或混用策略。

## 验证原则

类型检查、构建、TypeScript/Python 回归与前端流程验证分别留证。受控 UI 测试只证明页面与协议行为；真实模型验收另外记录 Runtime、Judge、案例和回收结果。失败、上游模型调用异常及重新执行均保留，不以重跑覆盖原记录。
