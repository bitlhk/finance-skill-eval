# Skill 迁移与优化能力演进方案

本文记录 `finance-skill-eval` 后续演进的目标、职责边界和实施顺序，供 Eval 与外部 Builder 开发时共同核对。它是**设计方案，不是当前能力说明**；实现状态以源码、契约和测试为准。

实施进度（2026-10-05）：方案版本、跨 Launcher 对比、脱敏事件摘要、Builder v1 `rebuild`、独立留出复核和目标驱动改进工作台已接入。任务能在预算内依据开发集证据选择 Skill/Tool 修复，生成独立候选、逐工具验证和复评；遇到 Harness 或配置问题则持久化等待，交付准入后沿用冻结题集恢复。Builder 已接入真实 Construction Agent、独立产物发布和宿主合同测试，不再只有包执行入口。配置值和凭据不提供给规划模型；采用候选仍需明确选择。具体边界、真实模型验收和仍需由部署方提供的适配器见本文末尾；不应据此宣称支持任意框架或能力。

核心决定是：迁移以 Skill 可复用为中心，不以某次目标 Runtime 运行成功为终点。出方案时就要明确脱离原框架后在哪些契约和条件下能够复用，以及原业务语义如何保留；实施和测试分别检查方案落实与运行证据。优化在同一份约束下依据评测证据提出更好的方案，不能悄悄缩小复用范围。一个方案由 Skill 文档和资源、Tool 实现与依赖配置、必要 Launcher/Harness 能力共同组成。修改哪一层应由证据决定，不能预设为“改提示词”或“让 Builder 重新生成”。

## 目标与非目标

目标是处理形态各异的企业 Skill：理解源工程的能力、工具、数据流、依赖和 Runtime 耦合；先提出有证据的可复用设计，确认业务行为、部署条件、数据关系与未知事项，再生成独立候选并在真实 Runtime 中验证。方案自由设计，不靠不断增加固定场景选项扩展。规划 agent 可以改变策略，但每轮仍要给出改动原因、预期效果和验证方法；若改变已确认的复用条件，需要形成新方案并重新确认。

本项目不为某一种 Tool、某一套接口或某个 Agent 框架写专用迁移剧本，也不把所有源代码都交给 Builder 重写。可保留的业务工具应尽可能迁移为 MCP 或 Script；Builder 仅处理无法在这一边界内表达、确需目标 Harness 承担的能力。框架注册胶水本身不是必须复刻的业务能力。

自动评测不等于生产授权或专业签署。系统可以推荐和验证候选，但涉及业务语义、权限、副作用或上线取舍时，由用户确认。失败且证据不足时应说明缺口并暂停，不猜测源行为。

## 当前基线

以下为写本文时的源码事实，不代表目标设计已经完成。

- 迁移已有检查、逐 Tool 方案、候选生成、Runtime 适配、技术验证、效果评测与导出流程；页面和后端按阶段推进。参见 `src/migration/domain/migration-workflow.ts` 与 `web/src/MigrationPanel.tsx`。
- 候选 Skill 有资产摘要和历史，评测记录候选摘要、测试集与配置指纹。参见 `src/migration/domain/migration-project.ts` 与 `src/migration/application/migration-evaluation-service.ts`。
- Builder 需求由诊断发现的 Runtime 能力生成；交付的是已部署 Launcher 的描述，Eval 读取 capabilities 并独立完成准入验证。参见 `src/migration/domain/migration-harness.ts`、`src/shared/contracts/runtime-builder.ts` 与 `contracts/runtime-launcher/README.md`。
- Launcher 提供实例创建、执行、销毁和标准化运行证据。标准事件保留原生事件来源，但可移植消费方不能依赖框架专有字段。参见 `docs/runtime-launcher-protocol.md`。
- 现有优化器从一轮已完成评测出发，一次模型调用只修改 `SKILL.md` 或 `references/*.md`，生成候选并复评；不能修改 Tool、配置或 Harness，也不是可反复推理和试验的 agent。参见 `src/service/optimization-manager.ts`。
- 现有迁移成对评测要求左右绑定同一 Launcher，适合控制运行环境后比较 Skill 版本，不足以表达新旧 Launcher 的整套方案对比。参见 `src/shared/contracts/run-configuration.ts`。

因此，下一步不是增加一种特定 Skill 样例或再加一个固定页面步骤，而是补齐“完整方案版本、实验记录、证据驱动的改动循环”这三个基础能力。

## 职责边界

| 责任方 | 应负责 | 不应负责 |
| --- | --- | --- |
| Eval | 源工程诊断、用户确认的目标与测试方案、迁移和优化规划、Skill 与 Tool 候选、实验编排、证据与版本管理、Builder 需求、交付准入、结果解释 | 在本仓内实现外部 Builder 的框架适配代码；把评测结果宣称为生产授权 |
| Builder | 根据明确的能力需求构建、验证并部署目标 Launcher，返回可追溯的交付 Result；将原生回调映射为契约规定的证据 | 决定 Skill 的业务迁移方案、生成通用业务 Tool、判断业务效果是否提升 |
| Launcher | 按协议隔离实例、加载本轮 Skill/Tool/配置、执行测试 case、返回结果和声明过的观测事件、清理资源 | 替 Eval 选择测试集或优化目标；泄露密钥、原始敏感数据或隐藏推理 |
| 用户 | 确认目标与测试方案、业务语义和高风险变更、选择是否采纳或发布 | 为每个未知 Skill 预先编写平台规则 |

Builder 交付描述不携带模型密钥或 MCP 密钥。Eval 的准入验证不能以 Builder 自报的验证结果替代。已有 Launcher 契约仍是接入基础；只有确实出现不兼容的语义变化时才升级版本，不为每轮优化制造一个新协议版本。

## 统一的改进循环

每个任务先冻结目标和约束，再重复以下过程，直到达到验收条件、预算耗尽、需要用户决定或证据不足：

1. **观察和归因。** 汇总源文件证据、静态诊断、技术验证、最终 execution evidence、Judge 结果和 Launcher 声明支持的观测事件。区分业务质量问题、Tool 行为问题、配置或数据流问题、Runtime 能力缺口与评测环境故障。观测缺失只能降低诊断置信度，不能自动判定业务失败。
2. **提出可证伪的假设。** 说明问题证据、拟改动的层、预期影响、可能回归、要运行的测试及停止条件。一个失败 case 可以有多种候选解释；agent 不应把 Judge 评论直接当作代码修改指令。
3. **生成独立候选。** 从明确的基线派生新版本，不覆盖源资产、已验收候选或已交付 Launcher。改动 Skill/Tool 时生成新资产；改动 Harness 时向 Builder 提交新的构建需求并等待新 Launcher；仅修改运行配置时记录新配置摘要。每轮保留文件差异和构建来源。
4. **分层验证。** 先验证契约、依赖、启动和 Tool 行为，再在开发测试集上检验任务效果。失败应回到诊断，而不是继续叠加提示词。必要时 agent 可修改假设或选择另一层，但必须留下每轮结果。
5. **独立复核与选择。** 最终候选使用冻结留出集复核。结果呈现收益、退化、不确定性与条件变化；用户决定采纳、保留旧版或继续试验。采纳只改变本项目选中的候选，不自动替换生产 Skill 或 Launcher。

这是一套目标驱动流程，而不是给每种 Skill 预先分配固定分支。为保证可控，agent 应有轮数、时间、模型调用和构建次数预算；确定性校验、权限边界、资产身份和秘密处理由平台执行，不交给模型自行遵守。

## 方案与实验的版本模型

需要新增一个跨迁移和优化共用的“方案版本”。最小身份应包含：Skill 资产摘要、Tool/依赖产物摘要、Launcher 的 `deploymentId` 与 `artifactSha256`、运行配置摘要，以及它所基于的上一方案版本。某层未变化时沿用其引用，而不是复制或重建。部署地址和凭据不是方案身份；执行绑定另记指纹，地址变更使旧执行验证过期。凭据值不进入记录或模型上下文。

每次实验绑定方案版本、目标、测试集版本、开发/留出划分、测试数据快照、模型及参数、Launcher capabilities 摘要、执行证据和 Judge 版本。记录结构化的假设、改动、验证、结果及采纳决定，使任何一条结论都能回答：“比较了哪两个完整方案，保持了什么不变，改变了什么？”

现有 `MigrationProject`、Skill 资产、评测 Job 和 Optimization 记录应先通过引用接入统一视图，避免立即迁移或重写全部历史数据。新版本不能仅靠 `candidateDigest` 判断实验是否仍然有效：Launcher、配置或测试集变动同样会使旧结论失效。

## Builder 重建与接入

接入进展（2026-10-05）：Builder 已新增显式启用的可信本地包执行后端，能运行 Eval 交付的 Script/MCP，
不重写业务工具；它与银行准入后端分离，共用 Launcher v1 生命周期。Eval 同步补充可选 `skill.skillFile`
及完整包路径传输，避免嵌套 Skill 文档与同级 MCP 工程错位。底层真实模型已验证工具间 MCP 状态、交付
脚本、无 Skill 对照和 case 文件隔离。这一步是执行接入，不代表根据任意能力需求进行 Harness 构建已经
完成。随后已接入 `RuntimeConstructionAdapter` 与受管包发布器：真实 Construction Agent 在隔离模板
内修改 Runtime，宿主重新核对实际差异、确定性归档与加载摘要，执行独立合同测试后才形成 Result。
当前实现依赖服务端批准的模板、写入范围和按合同摘要匹配的验证器；不支持的能力关闭失败，不把
“能执行 MCP/Script”伪装成“已实现任意 Harness 合同”。

本轮接入验收：真实 A2/A4 和测试集模型从 `acceptance/openjiuwen-portability/legacy-skill` 生成产物后，
通过 `scripts/verify-migration-v2-ui.mjs` 的外部 Launcher 模式在页面执行。首次接入发现嵌套入口错位、
Windows 隔离 Python 的 UTF-8 管道解码，以及仅摘要证据不足以核对工具事实三个问题。修复后复用同一
产物和冻结测试集从页面复测，真实 Builder/OpenJiuwen 执行与真实 Judge 的 3 个案例全部通过。工具
结果证据仅在 Builder 私有配置显式启用时提供有大小限制的脱敏投影；未启用或证据不足时仍允许 Judge
报告无法判定。另有 4 个底层真实模型案例验证 MCP 状态、Script、无 Skill 基线与跨 case 文件隔离。

只有证据指向 Harness 缺口时才请求 Builder。请求应表达所需**行为**，而不是指定框架内部的实现步骤：输入、输出、错误语义、权限、副作用、隔离要求、消费它的 Tool、来源证据和验收用例。还应关联本轮基线方案、先前 Launcher 与需求摘要，便于判断是新增能力、修正能力还是保持不变。现有 v1 的可选 `rebuild` 字段已承载基线部署、产物、方案版本、假设和实际运行证据，不另外创建 v2。

Builder 返回新 Result 和新 Launcher 描述后，Eval 按现有准入流程重新读取 capabilities，并实际执行创建、运行、证据校验、销毁。通过准入只说明 Launcher 符合协议；随后仍须用本轮 Skill、Tool 和测试集验证目标业务行为。若 Builder 拒绝、交付不完整或复测失败，旧方案保持可用，失败证据回到下一轮规划。等待外部 Builder 时任务应可暂停和恢复，不能让一次长时间模型调用占着整个流程。

## 评测与归因规则

用户仍需选择或确认测试目标、关键业务路径和可接受的验收标准；agent 可建议补充案例，但不能自己决定“考什么”后再宣称通过。开发案例用于定位和迭代，冻结留出案例不能进入候选生成的提示词、文件上下文或多轮反馈。若留出集被反复用于调参，它必须降级为开发集并重新准备独立验收集。

评测至少区分两类结论：

| 对比类型 | 条件 | 可以得出的结论 |
| --- | --- | --- |
| 受控 Skill/Tool 对比 | 同一 Launcher、模型及参数、配置、测试数据，仅候选资产变化 | 在这些条件下，候选资产带来的效果差异 |
| 整套方案对比 | Launcher/Harness、配置或多个层同时变化 | 新方案相对旧方案的端到端效果差异；**不能**单独归因于 Skill 文档或 Builder |

跨 Launcher 对比需要允许左右分别绑定已准入部署，同时保存双方 capabilities、实际模型映射、依赖配置和数据快照。模型名称相同不等于模型、权限和工具环境相同；不满足可比条件时应显示差异并降低归因等级，而非伪造单变量结论。原服务对比、候选目标评估和同条件 A/B 仍保留各自含义。

Tool 启动或调用失败首先进入技术故障诊断；它不是专业输出较差的证据。验收主要依据最终 execution evidence 和明确的业务断言；更细的观测事件帮助解释原因，但 Launcher 未声明支持的事件不能作为通过门槛。

## 页面与接口演进

保留现有迁移方案让用户确认关键选择，但将“实施、测试、优化”呈现为同一个任务工作台，而不是不断增加线性页签。工作台首先显示目标、当前方案、当前阻塞和建议动作；每轮实验可展开查看证据、假设、改动文件、Builder 请求和结果、测试失败及版本对比。只有确需用户判断的节点要求确认，后台可继续完成已授权的验证。

后端先建立统一的方案和实验读模型，再提供启动/暂停/恢复改进任务、记录用户决策、提交或接收 Builder 交付、比较方案的接口。API 的具体路径以实现时的路由结构决定；不要先为 UI 新建一套独立于现有迁移与评测服务的数据存储。现有单次文档优化入口可作为兼容入口，在统一实验模型稳定后再决定是否收敛。

## 实施顺序与阶段验收

1. **版本和证据基座。** 定义方案版本、实验、假设与结果的最小模型；将现有迁移候选、Builder 交付、运行 Job、优化记录关联起来。验收：任一结果可追溯完整执行组合，任一层变化会使相关旧验证标记为过期；旧记录不必重写也能继续读取。
2. **受控的局部优化循环。** 让 agent 基于开发集、技术结果和允许的观测事件定位问题，先支持 Skill/Tool/配置候选的有限轮试验；建立差异、预算、失败归因和人工决策。验收：能发现工具故障并转向修复或暂停，不会用改 `SKILL.md` 掩盖故障；留出题不泄漏给编辑 agent。
3. **Builder 往返闭环。** 与 Builder 项目确认迭代需求字段和交付语义，支持新 Launcher 准入、重测、失败回退和暂停恢复。验收：Harness 确需改变时可以从证据提出需求，接收新部署并完成真实端到端评测；Builder 未交付不会破坏旧候选。
4. **跨 Launcher 对比和工作台。** 支持整套方案对比及明确的归因标签，将迁移与优化轮次统一展示。验收：用户能看到每轮改动、比较条件、收益和退化，并明确选择保留哪个方案。

每阶段都应有契约测试、服务层测试和至少一条通过前端操作的端到端路径。端到端案例至少分别覆盖无需 Builder 的迁移、确需 Builder 的迁移、局部优化和 Harness 重建后的优化；案例用于验证通用机制，不应反过来成为硬编码业务规则。

## 暂不预定的决策

- 外部 Builder 的调度传输方式由部署方选择。目前使用已有需求下载和 Result 准入接口，并支持持久化等待与显式恢复；不预设 Builder 的私有任务 API。
- agent 的具体运行框架、工具集合与最大预算，应由第一阶段的证据模型和实测成本决定，不先按某个 Skill 场景写死。
- 跨 Launcher 对比在模型或能力无法对齐时的最低可比要求，需要结合真实 Builder 交付验证；即使能执行，也应允许结论是“不可归因”。

这些待定项不改变本文的职责边界与验收原则。后续实现若要偏离，应在本文件记录原因、替代方案及其对证据和归因的影响。

## 当前落地边界（2026-10-05）

`MigrationImprovementTaskService` 复用既有规划、Skill 编辑、Tool 编辑、技术验证、评测及 Builder
准入服务，不另建一套运行引擎。任务与轮次保存在原 MigrationProject；每个候选仍是不可变 Skill
资产。前端“持续改进任务”提供进度、停止、逐轮改动与评测证据、等待 Builder/配置及采用操作。

- 从当前候选的目标评估启动；必须具有冻结开发集、独立留出题、运行配置与方案版本证据。
- 最多 1–5 轮、60–7200 秒；时间到中止模型请求及运行，连续两轮无提升停止。Builder 等待时间
  不占执行预算，恢复仍沿用剩余预算。配置、候选、Launcher 身份或私有试运行参数中途变化时停止。
- 规划读取有限源码、开发集评测与稳定错误码；不读取留出题、密钥或私有试运行参数。Tool 修复限定
  在已有工具文本文件；Skill 修复复用现有编辑器；两者必须再做真实技术验证。
- 仅当通过案例严格增加且已通过案例无退化时，才保留新方案；工作中的项目候选不自动切换。
  某个 case 的 Runtime 失败不会抹去其他已通过 case 的保护。Judge 服务故障不视为业务退化；开发集
  仅对同一候选原样重试一次判定，仍失败则停止。最终留出复核不因 Judge 故障重复执行。
  明确的执行模型调用故障直接停止，不重放可能已产生副作用的 case。规划输入包含匹配的工具技术
  验证及运行记录完整性；不完整记录中的空调用数组不能作为“工具未注册或未执行”的事实。

## 复用验收与交付结论的实现边界

复用验收通过现有测试集、Launcher 与业务 Judge 执行，不再以源码审查或普通业务题通过代替。
已确认方案中的原始验收标识逐项关联执行案例；执行计划经过独立覆盖审查，并由用户明确确认。
候选、源码审查、方案、运行配置、Launcher 能力和执行模型共同绑定，变化后旧结果失效。
覆盖审查的 `status` 表示是否完整覆盖，`reasons` 解释该状态；通过依据不应被当作阻塞项。

现有执行原语为：运行组使用新的 Runtime 实例；独立案例使用独立原生会话、工作区与工具生命周期；
一个多轮案例内才保留会话、工作区和 MCP 生命周期。真实多轮以每轮查询/输出摘要和实际工具调用回执验证，
不使用拼接的模拟对话。单条 `turns` 表示可无损转换为普通单轮，不补造第二轮。
新实例不是新的 Launcher 部署，现有原语无法覆盖的原承诺必须阻断，不得冒充已经执行。
回执是 Launcher 的执行声明，不是独立的 OS 隔离证明；临时句柄续接只验证同任务生命周期，
不能单独证明 Skill 在新环境中可复用，也不要求旧句柄跨实例存活。

评测器还会对已知的案例输入做摘要匹配，不向 Judge 发送整份工作区文件或原始工具入参。
对于已挂载且摘要一致的数据，`workspaceInputMatches.FILE_READ` 核对 `read_file` 的工作区实参
及完整返回内容是否恰好匹配当前案例文件；`TOOL_ARGUMENT_VALUES` 按已声明的 Script 输入 Schema
选择 JSON 文件字段，核对实际工具实参摘要是否完全一致。只有实际成功调用且摘要匹配才产生事实。
这证明读取/入参的值一致，不证明程序级因果数据流；未知合同、格式变化、未提供 Schema、脱敏后
摘要不同或 MCP 输入转换等情况不会凭空得到匹配结论。原承诺依赖这些缺失证据时仍须无法判定或阻断。

只有全部复用要求通过后，才为实际成功调用过的候选工具写入集成验证记录。
业务评测与复用运行分别记账，后者不能替代用户选择的业务评测。
下载页分别展示方案落实审查、业务评测和复用验收；工具/依赖就绪、当前方案审查符合、
业务评测通过及当前复用验收通过后，才标记自动检查完成。仍可下载未验证包，但文件名带 `-unverified`。
标记不代表生产授权或专业签署。打包返回实际候选摘要，导出结论不得套用其他版本的检查结果。
