# 刘思达实例审核技能与当前精选审核助手对比

核查日期：2026-09-05。结论：建议优先纳入“信贷审核规则生成”专项候选，不直接替换当前智能审核岗位助手。

## 资产确认

本次只读查询上海 EA 的技能市场、维护人记录和刘思达的审核岗位实例，未修改 EA、个人技能文件或发布状态。

| 资产 | 身份和状态 | 本次比较用途 |
| --- | --- | --- |
| `smart-audit-assistant` | 平台维护；上海已批准 1.1.0；主文件、两份专业 SOP、manifest 与当前精选来源目录逐文件一致 | 左侧岗位助手 |
| `credit-audit-rule-generation` | 刘思达实例个人上传；未声明版本；未找到对应个人市场发布身份 | 右侧规则生成专项 |
| `credit-audit-borrower-qualification` | 同上 | 右侧借款人资格专项 |
| `credit-audit-income-verification` | 同上 | 右侧收入核验专项 |

“刘思达实例个人上传”是核实到的提供者关系，不等于已确认每个文件的原创作者。三个包均包含 SKILL.md 和两份参考文件，版本以冻结文本快照摘要识别，不冒充 1.0.0 等发布版本。

初查发现的 `smart-audit-suite` 是另一个本地实例中的 22 子技能包，并非此次确认的刘思达实例上传资产。本次执行没有使用该包，不能把其文件数量、脚本依赖、偿债阈值等特征归到刘思达这三个 Skill 上。

## 方法与边界

- 三道固定模拟材料题：收入交叉验证、主体资格、制度转规则。每道题左侧使用岗位助手，右侧使用对应专项 Skill；不是同一右侧 Skill 连续做三题。
- 双方使用相同题面、OpenJiuwen 0.1.17.post1、GLM-5.2 和完整参考文件挂载机制；执行顺序交替。每题每侧执行一次，共六次成功执行。
- 题面提供模拟制度和已解析材料；不连接业务 MCP，不核验真实客户资料或原始影像，不执行授信审批。
- 复用 Finance Skill Eval 的 `ModelPairwiseJudge` 和 Codex CLI 适配器，由 GPT-6-astra 匿名评价专业匹配、完整性、表达和可执行性。
- 本次脚本直接调用标准 Runtime HTTP 接口，是定向对比，不声称由 Promptfoo 跑批，也不是公开 UI 已新增的历史任务。
- 这是“岗位主技能 vs 对应专项技能”的小样本比较，不证明无 Skill 增益、完整审核工作流能力或生产适用性，不是独立人类专家签署。

首轮尝试默认 GLM-5.3-Flash：左侧输入 3449 tokens，输出用量 6000 tokens，但未返回正文，Runtime 标记 `Model returned no answer`。不能据此评价 Skill 专业质量。该轮随后停止，保留失败证据，临时会话已回收；上述六次成功执行全部使用 GLM-5.2，Demo 默认模型未改。

## 对比结果

分数顺序：专业匹配 / 业务完整 / 表达清晰 / 可执行性；各项 0 至 4 分。

| 任务 | 岗位助手 | 刘思达实例专项 | 校正后的 AI Judge |
| --- | --- | --- | --- |
| 收入口径与材料勾稽 | 3 / 4 / 3 / 4 | 3 / 4 / 2 / 3 | 岗位助手，小幅优势 |
| 主体资格与条件性凭证 | 4 / 4 / 3 / 4 | 3 / 4 / 3 / 3 | 岗位助手 |
| 制度转换为规则草案 | 3 / 3 / 2 / 2 | 3 / 4 / 3 / 2 | 规则生成专项，小幅优势 |

### 收入核验

双方都正确识别：税前月薪 2 万元、扣缴 0.2 万元、实发 1.8 万元可以勾稽；本人账户调拨 0.5 万元不计收入；社保基数 1.2 万元不直接否定工资收入。

岗位助手的结论和补件意见更集中。专项版本额外展开与本题无关的后续材料提示，并把个税六个月汇总值描述得像逐月明细。双方均把多份材料称为独立来源，超出了题面给出的证明范围。

### 主体资格

双方都算出 35 周岁，确认三份材料主体一致，并识别未婚者不需要结婚证。岗位助手证据归属更准确；专项版本把题面日期归入未明确指定的具体凭证，还增加替换模拟证件引用的建议，超出固定虚构案例的任务范围。

### 规则生成

专项版本把四条制度分别映射为规则，字段一致，逐条引用完整，覆盖未婚不适用和缺件处理，适合作为规则结构化的专项资产。

双方仍有交付缺陷：对完整响应执行 `JSON.parse` 均失败。岗位助手有 Markdown 围栏和额外说明表，专项版本有读取旁白。不能将“内部含合法 JSON”说成“下游可直接消费”。Runtime 当前会串接流式文本，此项需要区分最终答案格式与中间旁白处理，不能只归因于 Skill。

## 阅卷校正

初轮匿名 Judge 将“匿名证据中省略 read_file”误读为“没有读取模板”。原始运行证据确认双方实际读取了参考文件，因此这项扣分依据不成立。

本次仅在统一 Judge 提示中澄清这个证据展示边界，不修改执行答案、题目或评分维度，对三组原输出全部重新阅卷。初版 `*-judge.json` 与校正版 `*-judge-v2.json` 均保留；表格采用校正版。规则生成题从原先左侧优转为右侧优，也说明不能把一次 AI 阅卷直接视为最终事实。

## 源码层面的互补与改进

| 方面 | 当前岗位助手 | 三个专项 Skill |
| --- | --- | --- |
| 定位 | 岗位入口、任务选择、证据矩阵、审核意见 | 单项任务的输入、步骤和固定产物 |
| 专业优势 | 主体/期间/口径对齐，最小补件，工作意见组织 | 制度到规则映射，资格逐条核验，多凭证收入交叉验证 |
| 适配方式 | 当前精选已有模拟案件 MCP；本轮用提供文本 | 三个现有包均可先走文本和规则输入，不必为展示额外配 MCP |
| 待改进 | 精简重复内容；改善规则 JSON 交付 | 避免固定凭证优先级替代口径分析；补充证据不足、不适用等状态；声明版本与提供者 |

收入专项的固定“税务、社保、流水、收入证明”优先级以及默认规则需要与机构实际制度核对。这是待验证的设计风险，不代表本轮已经发生错误；本轮专项答案正确消费了题面给定的口径规则。

规则生成包声明四个下游专项，但此次实例只找到其中“主体资格、收入验证”两个，未找到声明的资产负债与偿债能力包。因此暂不展示为“四项完整自动审核闭环”。

## 建议入选方式

1. 保留当前“智能审核岗位助手”，不直接覆盖或改换作者。
2. 优先把 `credit-audit-rule-generation` 作为“信贷审核规则生成”专项候选；先解决纯 JSON 交付，冻结原始来源与版本说明，再进入精选。
3. 主体资格、收入核验作为独立专项资产保留，改进证据归属和输出范围后补更多材料缺失、冲突、制度变化的题目；不一次把全部审核素材打包宣称完全支持。
4. 当前 Demo 尚未新增这三个精选入口；本次只新增核查报告与对比脚本，未改原 Skill、业务环境或公开精选列表。
