# Finance Skill Eval 2.0 特性说明

## 1. 产品目标

**这是一个 Skill 评估产品。** 它交付的是"这个 Skill 好不好、以及改到更好之后确实变好了"的结论。Skill 标准化与 Tool 迁移是第一阶段——不是产品本体，是让评估得以成立的前置。

系统分两阶段回答：

**阶段 A 准入门槛**——"能不能用"：

1. Skill 写法是否符合企业规范；
2. 每个 Tool 是否已经可以跨 Runtime 使用；
3. 哪些 Tool 需要迁移，以及适合迁移成什么形式；
4. 迁移后的 Tool 是否能独立运行。

**阶段 B 评估**——"好不好用"：

5. Skill 和 Tool 在 OpenJiuwen 中能否共同完成任务；
6. Skill 优化后是否真正带来改进。

阶段 A 的出口全是确定性的，不需要人评判。

Skill 合规判断以独立的企业 Skill 规范为依据；本文件只定义迁移产品要提供的能力。

## 2. 目标用户

- 需要迁移企业 Skill 的业务和研发人员；
- 负责 Tool、接口或脚本的开发人员；
- 负责验证业务结果和权限边界的评审人员；
- 负责 Skill 评估和优化的团队。

## 3. 首期使用前提

- 输入代码来自企业内部可信来源；
- 在运行本项目的同一台机器上执行一次性技术验证；
- 最终 Agent Runtime 验证目标是 OpenJiuwen；
- 生产部署、远程 Worker 和真实业务办理不在首期范围。

## 4. 用户流程

```text
【阶段 A 准入门槛】
导入工程
  → 查看 Skill 与 Tool 检查诊断（含建议形式与建议语言）
  → 逐 Tool 授权（形式必选，语言可选）
  → 改造 + 验证循环（生成 → 编译 → 契约测试 → 加载检查 → 回灌）
  → 准入：代码符合源契约 + Skill 合规可加载

【阶段 B 评估】
  → 运行 OpenJiuwen 验证
  → 评估并优化 Skill
  → 复测并导出
```

## 5. 特性清单

本文定义**产品特性与验收标准**。每条特性的**实施拆解**（工作项、类型、依赖顺序）见 [impl/](./impl/README.md)——拆解文档不重复验收标准，只引用这里。

### F-01 导入工程

用户上传待迁移源码 ZIP。**导入只做三件事：解压、算摘要、安全限制——不判目录格式。** 真实的源工程不会长成固定布局，后续的检查诊断是一个 agent，有能力自己查看目录结构。

验收标准：

- 原始上传内容按摘要（`artifactSha256`）保存，后续步骤不覆盖原资产；
- 摘要必须是所有下游证据的绑定点；
- **不强制目录格式**：不要求根目录必须是 `skill/`、`tool/`，也不要求入口必须是 `skill/SKILL.md`；实际布局由检查诊断阶段识别；
- 安全限制必须保留：解压体积与文件数上限、符号链接拒绝、重复路径拒绝；
- 二进制和无法读取的文件列入清单，不在扫描阶段执行。

### F-02 Skill 规范检查

用户可以单独查看 Skill 是否符合企业 Skill 规范。

验收标准：

- 检查唯一且大小写准确的 `SKILL.md`、`name`、`description` 和引用文件；`SKILL.md` 的位置由导入阶段识别，不预设固定路径；
- Skill 包内交付时只保留 `SKILL.md`、`scripts/`、`references/`、`assets/`；可执行脚本放错目录属于待迁移错误，不阻塞生成；
- 展示可定位到文件和行号的问题；
- 区分错误、警告和提示；
- 不把 Tool 的实现语言当作 Skill 合规条件；
- 检查过程不执行上传代码。
- 所有 Skill 规范错误进入迁移计划，生成器修复 frontmatter、入口名、目录、重复入口和文件引用，再对候选包重新执行合规检查。

### F-03 逐 Tool 可移植性检查

系统发现工程中使用或实现的 Tool，并为每个 Tool 给出证据、状态和建议。

验收标准：

- 至少识别 MCP Tool、命令行 Script Tool 和 Runtime SDK 绑定 Tool；
- **分析的产出是对 Skill 的分析**：用到了哪些工具、每个工具的输入输出、样例。它同时是**基线**（迁移保留什么、校验比什么）和**出题的种子**；
- 分析**不靠"捞"**：不扫散文里的反引号当 Tool 名、不靠正则从源码刨 `inputSchema` 字面量、不靠模型凭空填 Schema——源里未必存在那个东西；
- 检查诊断是一个 **agent 循环**：能读文件、grep、枚举目录，也可调用静态扫描器；
- 静态扫描器**不是必经前置**，而是 agent 可调用的工具之一。保留它是为了**覆盖率**——它按构造枚举全部文件并报告哪些读不了，因而能回答 agent 回答不了的”我漏了什么”；
- 模型的每条发现只有在文件路径、行号和连续原文片段均与上传快照一致后才成为证据，否则拒绝；**分析读出来的工具与输入输出同样要落到证据上**；
- 未完整覆盖但与任何 Tool 无关的文件保留提示；未完整覆盖 Tool 相关源码时必须人工确认后才能生成；
- MCP 是否可移植不取决于 Java、Python 或其他实现语言；
- 对每个 Tool 展示名称、来源文件、语言、状态、问题，以及**建议形式与建议语言**；
- 状态包括 `PORTABLE_MCP`、`PORTABLE_SCRIPT`、`RUNTIME_BOUND`、`INCOMPLETE`、`UNSUPPORTED` 和 `UNKNOWN`；
- 证据不足时返回弃权，不硬给结论；
- 静态结果不显示为”已验证通过”。

### F-04 逐 Tool 授权

用户可以分别决定每个 Tool 的处理方式。

已经符合独立 JSON Script 协议的实现原样复用；其余 Runtime 耦合、跨语言或跨文件工具必须由配置的 `MIGRATION` 模型进行语义代码迁移。未配置模型或模型未返回完整入口时停止生成，不输出规则占位包。

**这是授权环节，不是技术评判。** 人工批准的是"这个 Tool 的业务行为可以脱离原系统运行"——这是合规与风控判断，系统无依据可作。"选哪种形式更可行"属于工程判断，系统应当给出建议。

验收标准：

- **形式必选**：每个 Tool 必须选择 `MCP` 或 `SCRIPT`；
- **语言可选**：不填则采用系统的建议语言；
- 系统为每个 Tool 展示**建议形式**与**建议语言**及其理由；
- 同一项目可以混合两种迁移方式；
- 选择 MCP 的多个 Tool 按实现语言合并到各自语言的 Skill MCP 服务；
- 每个决定绑定当前资产，资产变化后要求重新确认；
- 不要求用户填写迁移理由。

### F-05 改造与验证循环

系统根据逐 Tool 授权生成新的候选工程，并循环验证到达标。

**这是一个循环，不是单次动作：**

```
   生成 ──→ 合规自检 ──→ 编译 ──→ 契约测试 ──→ 加载检查
    ↑                                            │
    └────────── 失败原因回灌 ─────────────────────┘
```

验收标准：

- 原始资产保持不变；
- **MCP 生成语言不写死**：按同语言优先的判据算出，跨语言重写允许但计划里提示不推荐；
- **Script 生成语言为 Python 或 Node**；
- 同一 Skill 的**每种实现语言**只生成一个 MCP 服务工程，服务中可以包含多个 Tool；
- 生成能力范围不影响其他语言 MCP 的合规判断；
- 服务校验所有相对路径并拒绝路径逃逸；
- **代码由 agent 生成，含服务外壳与启动方式**；平台不生成服务、不往工作区播种，模板只作为技能包里的**指导**；
- 交付物包含**启动命令**与 README；
- **硬门禁只有三条：起得来、工具有、调得通**；
- 接口相对**基线**（分析读出来的输入输出）的差异**必须报告**并附每处改动的理由；**逐字一致不是门禁**——迁移必然做适配；
- **禁止用模型自写的测试输入当门禁判据**；测试输入用分析读出来的**样例**；
- 迁移后的代码在 **Skill 包自己的环境**里起，不是 agent 的环境；
- 失败原因回灌后重新生成；轮数上限与总时长上限必须显式；
- **agent 判定某个 Tool 无法忠实迁移时返回弃权，退回授权环节重新决策**，不交付占位或骨架实现；
- 循环每一轮记录轨迹（改了什么、哪层没过），作为审计证据；
- 所有自动改动按文件展示 Diff；
- 用户修改过的生成文件不会被静默覆盖。

### F-06 本机一次性技术验证

用户可以在本机验证当前候选中的 Tool。

验收标准：

- 每次任务使用独立临时目录，完成后清理；
- 只执行服务端允许的程序和参数，不执行模型拼接的 Shell；
- 支持成功、失败、超时和取消结果；
- MCP 验证覆盖启动、Tool 列表和 Tool 调用；
- Script 验证覆盖入口、结构化结果、退出码和错误；
- 支持**同一工作目录跨多次调用保活**，供改造循环中的 agent 读写、编译与跑测试；
- 在 **Skill 包自己声明的环境**里跑（`uv run` / `npm install` 等），不用平台的解释器；
- 启动方式用交付物声明的**启动命令**；
- 结果绑定当前 Tool 和候选摘要；
- 报告明确标记 `LOCAL_TRUSTED`，不宣称生产安全隔离。

注意与 F-05 的**契约测试**区分：技术验证判定"这个 Tool 能不能启起来、说的协议对不对"；契约测试判定"输入 / 输出形状有没有变"。两者都不判定业务值是否正确。

### F-07 OpenJiuwen 端到端验证（阶段 B）

技术验证通过后，用户可以在 OpenJiuwen 中验证 Skill 和 Tool 的协作结果。

**归属阶段 B。** 这一项判定的是"Skill 与 Tool 合起来能否完成任务"，属于能力评价，不计入阶段 A 的准入门槛（阶段 A 的出口见 F-05、F-06）。

验收标准：

- Host 加载当前 Skill 和当前 Tool 映射；
- 支持已验证的 MCP Tool 和 Script Tool；
- 验证必要 Tool 调用、业务结果和安全先后关系，不固定完整推理轨迹；
- 记录 Skill、Tool、Runtime、模型、用例和实际调用证据；
- 任一绑定资产变化后，旧验证自动失效。

### F-08 评估与 Skill 优化（阶段 B）

OpenJiuwen 验证通过后，用户可以复用现有开发题、Judge、Optimizer 和冻结留出题。

这是产品本体：前面所有阶段都是为了走到这里。

验收标准：

- 首次迁移验证对当前候选做绝对质量评分，不把同一个候选伪装成左右胜负；
- 优化复测比较 C0（迁移候选）与 C1（优化候选），使用同一组 Tool、Runtime、模型、数据和权限条件；
- Optimizer 只修改 `SKILL.md` 和明确允许的非执行资源；
- Optimizer 不修改 Tool 源码、依赖或测试；
- Optimizer 不读取冻结留出题；
- 优化候选重新运行开发题和留出题后，用户再决定是否采用。

### F-09 报告与导出

用户可以查看并导出当前迁移结果。

验收标准：

- 报告分别展示 Skill 检查、Tool 检查、逐 Tool 决策、Diff、技术验证和 OpenJiuwen 验证；
- 明确区分静态可移植、技术通过、端到端通过和历史证据；
- 下载 ZIP 只包含可部署候选工程；测试结果和验证摘要保留在服务内报告中；
- 默认不导出凭据、Worker Token、完整模型回答或敏感测试报文；
- 未完成验证的候选只能标记为草稿。

### F-10 0.1 历史兼容

用户仍可查看和导出已有 0.1 项目。

验收标准：

- 保留源资产、候选、Diff、评测、优化和复核记录；
- 旧模拟验证明确显示为历史夹具证据；
- 旧验证结论不自动成为 2.0 技术验证或 OpenJiuwen 验证；
- 旧项目可以从当前资产重新进入 2.0 检查流程。

## 6. 明确不做的事情

- 不自动恢复缺失的业务代码；
- 不根据函数名猜测权威 Schema；
- 不把 MCP 限定为 Java；
- 不把 Script 标准限定为 Python（生成能力首期为 Python / Node）；
- 不要求 Skill 增加 Tool 清单或环境安装步骤；
- 不执行生产发布或真实业务办理；
- 不宣称本机 Worker 可以安全运行任意不可信代码；
- 不证明迁移前后 Runtime 完全等价。

## 7. 完成定义

首期开发完成需要同时满足：

1. F-01 至 F-10 的首期验收项都有自动测试或可重复验证记录；
2. 一个 Runtime 绑定 Tool 可以生成 MCP 候选（按源语言）并通过契约测试与加载检查；
3. 一个 Runtime 绑定 Tool 可以生成 Script 候选（Python / Node）并通过契约测试与加载检查；
4. 一个项目可以同时包含两种迁移方式的 Tool；
5. 同一 Skill 中同语言的多个 MCP Tool 只生成一个 MCP 服务；
6. 一个缺少业务实现的负例**不被标记通过，而是返回弃权**；
7. 改造循环在编译或契约测试失败后会回灌并重新生成；预算耗尽时返回失败而非通过；
8. OpenJiuwen 验证后可以进入现有评估和优化流程；
9. 现有非迁移评测测试保持通过。

## 8. 确定性验收集

首期随仓库提供三类小型 Skill，用于重复验证不同工具组合：

- 混合 Tool：一个 MCP Tool 和一个 Python Script Tool；
- 纯 Script：一个带 `pyproject.toml` 的 Python Script Tool；
- 共享 MCP：两个同语言的 Tool 由同一个 MCP 服务提供。

混合 Tool 的公开业务用例覆盖正常订单、订单不存在、订单未批准和 Script Tool 输入异常；另保留一个不同金额的隐藏订单，防止只针对公开答案实现。

运行 `pnpm test:ui:migration-v2` 可以使用真实本地服务和无界面 Chrome，重复验证页面上传、检查、迁移选择、
接口改动报告、从分析生成测试集、Script/MCP 技术验证与 ZIP 下载。测试不会调用企业模型服务，也不会读取本机模型凭据。

运行 `pnpm test:skeleton:mcp` 会把技能包 `references/service-templates.md` 里的 Python / Node / Java 三套
MCP 骨架**读出来**编译并起服务，用真实 MCP 客户端确认公布的 Schema 与源一致、调用打到业务方法。它需要
`uv` / `node` / `mvn`，且 Python 与 Node 首次要联网取依赖——所以它现在只在开发机上跑，没进 CI。

运行 `node --env-file=.env.local scripts/verify-real-agent-migration.mjs` 会**用真模型**把 A2 分析 → A3 授权 →
A4 交付 → 从分析生成测试集跑一遍，断言基线读出来了、交付物可试运行、测试集题目用得上分析里的工具。
它要模型密钥，因此同样不进 CI——但前面那些打桩的检查都替代不了它：agent 数不准行号、模型连接会断，
这两件事都是它第一个发现的。
