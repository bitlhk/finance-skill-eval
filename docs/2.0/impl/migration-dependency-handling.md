# 迁移中的依赖识别与处理

修订日期：2026-09-17。

本文规定迁移服务如何处理依赖，是诊断、迁移和测试的设计依据，不是 Skill 交付标准。交付要求以 [Skill 规范第 6 节](../skill-specification.md#6-tool-怎样做到与-runtime-无关)为准。当前落地范围见第 4 节。

## 1. 从源码判断依赖边界

依赖按实际职责区分，不能仅按“是数据还是 SDK”分类。判断必须记录源码或接口契约依据，不能只看变量或包名。

| 类别 | 示例 | 处理要求 |
| --- | --- | --- |
| Tool 代码依赖 | 业务接口客户端、计算库、凭证解析或签名库 | 可以保留在工具工程中，明确版本与安装要求 |
| 运行时依赖 | 业务调用所需的凭证、上下文、环境数据 | 在 Tool 中声明，由 Runtime 提供 |
| Runtime 的身份建立实现 | 登录、当前身份选择、执行凭证获取与刷新 | 不纳入 Tool 的业务实现，由 Runtime 负责 |

`auth_sdk` 不能整体判定为 Tool 依赖或 Runtime 依赖，应检查实际使用的方法。解析、校验已注入凭证的方法可以保留；建立执行身份或获取执行凭证的方法应移出 Tool。同一个 SDK 混合这些职责时，迁移应拆分调用边界；不能因保留解析方法，就继续依赖它的隐式登录状态。

例如，原调用链为 `user → auth_sdk 获取凭证 → 凭证 → 余额接口`，且 `user` 仅用于获取凭证，那么迁移后的余额 Tool 只声明它消费的凭证。若余额业务请求还独立需要用户标识，则另行声明该标识，并明确它是业务参数还是 Runtime 提供的上下文。

依赖类型和字段依据源码、类型定义或接口说明。不能从局部字段访问推断完整结构；证据不足时保留已确认部分并标记未知项，必要时要求补充契约说明，不要求提供真实凭证来代替类型说明。

## 2. 诊断、迁移与测试的责任

| 阶段 | 对运行时依赖的要求 | 对代码依赖的要求 |
| --- | --- | --- |
| 诊断 | 沿源码识别实际消费的依赖及执行身份边界，记录契约与依据；不要求填写真实用户数据或凭证 | 确认实现与调用契约，缺失且影响理解或转换时要求补充 |
| 迁移 | 将隐式依赖变成 Tool 声明和明确的注入入口，移出身份建立逻辑，保留允许的鉴权解析与业务行为 | 保留必要业务实现，整理构建和安装依赖 |
| 测试 | 根据声明配置测试数据、凭证和注入绑定，再执行工具；实际值不进入静态分析模型 | 准备可执行的代码依赖，验证真实工具实现 |

**缺少运行时依赖的实际值，不阻塞迁移。** 无法确定必需的依赖契约或实现边界，且影响可靠转换时，才需要补充说明或代码证据。不能把“还没有测试凭证”写成“无法迁移”。

迁移就绪表示契约和实现可交付；测试就绪表示测试环境已提供所需依赖；测试通过表示在该环境及用例上完成验证。三个状态必须分别记录。

## 3. 注入通道的传输映射

标准要求凭证和调用上下文通过独立、可信、按调用隔离的通道注入。具体接入契约需要按工具形式设计，不统一称为 header：

- HTTP 调用可以通过请求 header 传递，并明确名称、编码及可信来源。
- MCP 接入需要明确上下文如何关联到实际工具调用、如何进入工具实现，不能仅假定连接上的 HTTP header 就满足调用隔离要求。
- 本地脚本需要定义独立的调用元数据或其他注入机制，以及脚本读取方式；不能因为不存在 HTTP header，就将凭证改成模型可填写的业务参数。

以上是接入设计约束，尚未确定统一的封装格式。生成和测试必须使用同一份具体调用契约，不能生成一个只有平台内部隐式上下文才能运行的工具。

## 4. 当前平台实现

### 必需的静态诊断

A2 输出逐工具调用链和有源码依据的依赖清单。依赖分别记录 owner（Tool、Runtime、待确认）、action（保留、注入、移至 Runtime）和契约确认状态。Tool 代码是否可用与 Runtime 实际值是否已提供分开处理；必需的 Runtime 契约明确即可迁移，实际值缺失不阻塞。

共享依赖在统一区域展示；工具卡片展示自己的迁移形式、语言、推荐原因、链路与独立依赖。用户可上传缺失 SDK/资源或补充契约说明，再继续 A2。源码引用和补充实现引用由平台核对；文件存在不等于依赖实现已确认。部分分析保留已确认内容，执行失败不会覆盖已有结果。

需要 Runtime 上下文或凭证注入的实现推荐 MCP；当前 Script command 不支持额外注入，选择 Script 时阻止生成。选择 MCP 必须明确相应的 header 映射。

### 可选的提前连通验证

用户主动开启后，按 Runtime 注入依赖填写测试值。测试值单独保存在私有工作区，不进入源码分析、迁移生成输入或交付包；补充源码与契约说明则作为分析材料保存并记录修订。

提前检查仅支持用户确认的只读 GET/HEAD 业务接口，使用所选工具声明的 HTTP header，不执行原 Tool，不跟随重定向，也不保存响应内容。此检查不执行 Tool 的凭证解析或参数转换，不能代替生成后的实际工具验证。检查结果记录配置与依赖声明摘要；测试配置或声明变化后，旧结果失效。

### 生成后的实际调用

当前平台的调用映射为：MCP 上下文和凭证使用声明的 HTTP header，业务 arguments 保持独立；Script 使用通用 command，不额外注入 Runtime 依赖。这是平台的具体调用契约，不是 Skill 标准要求所有 Runtime 都采用的格式。

生成阶段只获得依赖声明，不获得真实测试值。存在必需的注入依赖时，编译和可执行的静态/接口检查先完成，实际业务调用明确标记待验证；不伪造凭证完成调用。

技术验证复用已保存的测试值，执行实际候选脚本或平台启动的候选 MCP 服务，验证结束后关闭该进程并清理工作区。后续 OpenJiuwen 评估只允许使用后端 `FINANCE_RUNTIME_CONFIG` 配置的本地 Runtime，不读取“测试环境”登记；前端展示的模型也从该 Runtime 配置脱敏生成。完整执行复用同一候选资产、启动命令、工具清单和 runtimeToolConfig，由 Runtime 为每次执行重新启动并清理候选 MCP。测试值优先通过环境变量提供，直接填写的值会随私有运行配置保存。MCP 工具的注入值使用独立调用客户端，避免多个工具共享可变凭证状态。敏感依赖在进入模型和公开运行证据前脱敏。

技术调用通过、业务接口连通和效果评估通过分别记录，不相互替代。当前不提供自动登录、凭证刷新、任意传输形式的上下文适配或真实外部写操作的提前探测。


## 5. 库依赖确认与安装验证

SDK 的 library 分类区分 STANDARD_LIBRARY、PACKAGE、CUSTOM_SDK、UNKNOWN，不改变 Tool 与 Runtime 的职责判断。分类需有真实 import 引用，标准库通过诊断进程提供的可信模块清单核对；Python 同名本地实现不能当作标准库。标准库不要求包内实现路径或上传源码。这里确认的是依赖身份和静态契约，目标平台上的导入可用性仍由执行测试证明。

第三方包通过 import、发行名和真实依赖声明确认。Node 支持 package.json 的运行依赖，Python 支持 project.dependencies、requirements 文件和 PEP723 dependencies；版本约束从声明读取，不采信模型猜测。缺声明时补充依赖清单或契约，不要求上传第三方包源码。发行名与模块名不同时，需要可信发行包元信息支持映射，不能随意配对。

企业 SDK 保持源码、资源和契约校验。不可读二进制不等于实现已确认，缺失且影响迁移时仍需用户补充。迁移 Agent 将已确认第三方包及版本约束写入交付依赖清单，使用包内环境运行；不安装标准库同名第三方包，不借用生成环境的全局安装。安装、导入与实际工具调用失败须保留明确失败结果。

已有显式业务参数和默认值（例如 workspace='workspace'）不得重新分类为隐式 Runtime 注入项。脚本相对 cwd 的工作区读写约定应保留，不因此强制将独立 Script 转为 MCP 或新增部署环境变量。
