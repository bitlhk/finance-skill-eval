# Skill 统一迁移与任务验收（单 Skill / 多 Skill）

## 使用方式

在「Skill 迁移」直接新建任务。一个任务导入 一个或多个 Skill，无需选择单 Skill / 多 Skill 模式；
同一个迁移 Agent 读取所选说明与依赖，可以同时修改多个 Skill、共享工具与入口指令。
每轮产出一个冻结整组候选，联合验收直接使用这个候选，无需到独立评测入口重新组装。

保留七个阶段：

1. **上传工程**：将 Skill、共享源码、依赖声明和资源一起打包为一个 ZIP；名称和补充要求可选。
   工程至少包含一个 `SKILL.md`，不限制 Skill 数量。也可复用已导入资产。整组工程保留相对目录；独立资产分别置于 members/member-N 下。
2. **诊断与迁移方案**：Agent 读取全部成员和共享源码，使用同一完整格式输出复用范围、保留的业务行为、源码依据、具体改造、依赖配置、运行条件、待确认事项和验收方式。
   页面先展示原有「Skill 指令 / 工具改造 / 运行与依赖配置」总览，再按工具展示当前实现、改造原因、迁移形式、改造前后、实施步骤、保留行为和调用链。共享工具与依赖只列一次，标注关联成员。
   完整工程方案和原始说明可展开查看；支持补充说明、调整工具形式、比较修订前后及查看历史方案。确认当前方案后才可生成。
   新诊断必须提供 `analysis.diagnosis` 与 `analysis.plan`，源码引用、成员和工具关联经校验后保存。仅有旧文字说明的任务按已有改造项分步展示，不推断缺失的改造前后事实、不改写历史数据。
   缺失信息只指阻止实施迁移、需要用户补充的内容；目标明确由运行时提供的业务数据，以及未要求的调度文件或 README 不应阻止生成。
   真实信息缺失时补齐工程重新导入；此版本尚无任务内源文件补充编辑器。
3. **生成迁移结果**：跨 Skill 改造并冻结完整候选。页面按文件展示前后内容和候选历史。
   静态入口、frontmatter、路径、服务文件与工具名称检查通过只表示清单有效，不表示业务验收通过。
4. **准备运行环境**：依据方案中的依赖和能力要求选择环境并核对。登记成功不代表满足要求；缺失的必需能力阻止运行，无法自动核验的条件明确标为待验证。
   需要新环境时，导出的运行需求自动包含方案中的能力合同。模型、入口指令和案例时限放在高级设置中。
5. **验证能否运行**：实际创建并释放实例，检查模型、容量和服务支持；
   实际启动、脚本/MCP 调用仍由联合验收验证。
6. **任务验收**：保存任务级测试集，用整组候选运行。失败后可点击「让 Agent 查看整组并修复」，
   生成新候选并整组重测。
7. **下载结果**：导出全部 Skill、共享文件、候选清单及有效验收报告。
   未通过的版本只能作为候选材料导出，不标记为已验收。

单 Skill 是只有一个成员的同一流程，多个成员时进行整组联合验收；不要求每轮修改全部成员，也不要求每个案例调用全部成员。

旧版任务在历史入口只读查看，显示不能继续执行的原因；原始数据和下载材料保留。已有统一任务缺少结构化方案时保留全文、按明确的原文标题分区，并说明缺项，不自动编造结论或重跑任务。方案重新分析后，旧候选和验收记录仍可查看，但需确认并生成新版本才可继续执行。详见[协议升级](production-deployment.md#协议升级)；代码与排障入口见[当前架构](current-architecture.md)。

## 统一集合协议

Runtime 使用 `finance.runtime-instance.v1` 接收 `skills[]`，不设置 Skill 数量上限；旧 `limits.maxSkills` 字段仅保留读取兼容，不作为准入条件。每个成员直接携带说明及可选资源，共享文件放可选 `assets`，不要求完整工程或 ZIP。路径和字节摘要固定实际验收版本。Builder 接收独立的 `finance.runtime-build-requirements.v3`，交付 `finance.runtime-build-result.v3`；需求与交付不携带 Skill 或业务任务回执，旧协议不再接受。

## 输入格式与边界

每个成员需要独立的 SKILL.md，YAML frontmatter 含非空字符串 name、description。
成员名称不能重复，入口不能嵌套。整组 ZIP 上限 8 MiB，展开后上限 32 MiB / 1000 文件。
目标 Runtime 有自己的容量限制，以能力检查为准。文件支持文本和二进制资源。

已有共享源码放在原有位置即可，不要求创建 orchestration/。
如果有供 Agent 使用的文本调度指令，可在运行配置中指定其工程相对路径。
第一版由原生 Agent 动态选择并使用多个 Skill；不解析或执行任意工作流引擎配置，
不将多个 SKILL.md 拼成一段大提示词，也不强制每个任务使用全部成员。
现有工作流若必须由专用引擎执行，需要单独的 Runtime 适配，分析时应报告这个缺口。

包内 MCP 的真实启动参数、文件清单和工具名由迁移 Agent 交付。已有外部 MCP 通过登记的执行环境绑定。
需要额外业务凭据或上下文的服务仍须在执行环境侧完成配置；不要把真实密钥写进源码或测试集。
托管账号沿用平台工具准入政策，不因整组模式放开自定义 MCP、脚本或 Harness 执行。

## 工作区与产物

迁移进程建立独立临时工作区：

```text
source/       原始完整源码，文件工具只读
candidate/    当前候选完整副本，Agent 可跨成员编辑
task/         成员清单、业务目标、目标约束、已确认方案及开发反馈
```

读/搜索工具可查看整个工作区，写/编辑工具只能写 candidate/。
分析阶段使用只读 Explore Agent，生成和修复阶段使用 Code Agent。
迁移阶段不开放通用 shell，只提供专用编译检查；整组尚无单工具合同注册表，
因此不挂载会始终返回 UNKNOWN_TOOL_CONTRACT 的单 Skill 契约测试工具。实际业务调用在联合验收时执行。
非空模型回答只有 JSON 格式损坏时，最多进行一次不带工具的真实模型格式修复；
空回答、执行错误和预算耗尽继续报告失败，不生成替代结果。
不将业务源码中的 skills/ 误当作 Agent 自身目录过滤掉。
生成失败或取消不会发布半个候选。进程临时工作区清理后，原始源码、已发布候选和失败状态仍由服务保存。
失败尝试重新发起时从上一个已发布候选重建工作区，不承诺恢复 Agent 未交付的临时修改。

持久化位于每个账号数据目录的 migration-tasks/：

- tasks/：任务、候选清单、尝试和验收记录。
- snapshots/：原始及各候选的完整文件快照，内容以 base64 保存。

成员内容未变化时继承成员版本与摘要，但每轮整体交付使用独立候选 ID。
共享文件属于整组摘要，即使成员摘要不变，共享依赖变化也会产生新的整组候选。
相同内容的不同迁移尝试仍是不同候选，报告不会自动转移。

## 联合验收与修复

测试集复用现有自然语言验收格式：

```json
{
  "name": "采购审核",
  "cases": [
    {
      "id": "over-budget",
      "input": "审核申请金额 8000 元、可用预算 5000 元的采购。",
      "criteria": ["明确指出预算不足 3000 元。", "不得声称申请已经批准。"]
    }
  ],
  "holdoutCases": [
    {
      "id": "boundary",
      "input": "审核申请金额等于可用预算的采购，说明判断依据。",
      "criteria": ["正确处理等于预算的边界。"]
    }
  ]
}
```

cases 和 holdoutCases 各最多 8 题，支持 workspaceFiles 提供案例数据。
每题创建独立 Runtime 实例，整组 Skill 在同一实例中可用，案例之间独立运行。
实际业务事实由执行模型取得；Judge 按每项标准判断，缺证据不能通过。
多轮案例仅在目标 Launcher 声明 multiTurn 时可执行；当前内置 Worker 不声明该能力。

每次验收冻结候选、运行配置、模型、环境能力、测试集和 Judge。
已装载成员由 Runtime 实测回执核对，Skill 激活与工具调用单独查看，不能把装载等同于调用。
取消、模型失败或未完成案例不算通过；工具失败的真实证据交给 Judge 按业务标准核验，不能用工具已装载替代成功调用。
回收信息保留 Runtime 实际回执；缺回执记录 UNKNOWN，不宣称资源已释放。

开发验收失败时，迁移 Agent 接收该次任务和真实结果/断言反馈，能够修改任意相关成员。
测试集与留出案例不会整体挂载进迁移工作区。留出失败不直接用于自动修复，
需通过开发回归案例重现；本系统不声称用户手工复制过的案例仍然保持独立。

当前实现手动触发「整体修复 → 整组重测」，不自动无限重试。
同一任务一次一个操作，进程内整组操作上限 2，重试 key 幂等且绑定完整请求。
重启会将未结束尝试标记 INTERRUPTED、未结束验收标记 INCOMPLETE，重新发起不会覆盖历史。

已验收导出要求当前候选、配置和测试集一致，最近匹配运行通过；
有留出案例时最近匹配运行必须为留出验收。导出前再次检查环境版本与能力；
环境变化需重验。下载成功不表示已经部署。

## Runtime 接入

Launcher 的一个和多个 Skill 使用同一实例接口，不设置数量驱动的模式。详见 [启动协议](runtime-launcher-protocol.md)。

## 接口与测试

所有新任务使用 `/api/migration-tasks` 和 `finance.skill-migration.task.v1`，存放于 `migration-tasks/`。保留历史文件与查看入口，不自动转换或删除旧任务；不能继续执行的历史任务展示具体原因，不能补造方案、运行证据或通过结论。API、UI 与 Runtime 需一起升级。

## Builder 统一接入

在「选择与配置 Runtime」导出能力需求，Builder 构建和验证 Runtime 后回填 Result。平台使用自有验证 Skill 进行独立准入，Runtime 交付绑定需求、能力、制品与部署。业务候选只在启动时注入。修改 Skill 或配置会使业务验收失效，能力仍满足时复用同一 Runtime。导出时再次核对在线环境和 Judge。详见 [Builder 接入](runtime-builder-integration.md)。
# 企业标准化与运行配置补充

新诊断使用 `enterprise-standardization.v1`：原能力基线、Script/MCP 可行性与改造/部署/维护成本、独立调用契约、源码覆盖清单和逐项验收要求共同绑定当前方案。一个或多个 Skill 使用同一套流程；历史记录不补造字段或升级结论。

服务地址、模型配置等由方案的 `configurationInputs` 声明，使用者在“准备运行环境”补充。缺实际值不阻止诊断和生成；必填配置未补齐时阻止运行检查及业务验收。普通配置保存实际值，凭证仅保存环境变量引用，解析值通过 Runtime 的私密通道传递，不写入候选源码或任务记录。配置已填写不代表实际连接或业务验证通过。

主配置与回退配置等任选关系使用 `configurationGroups` 声明：每组 `alternatives` 中至少一套配置必须全部填写。可以相互替代的字段不应同时标为单独必填；组合引用必须对应已声明字段，不能改变源码中整组或逐字段回退的实际语义。

支持 `toolEnvironment` 的 Runtime 将 `configuration["tool.env.NAME"]` 和同名前缀的 inline secret 映射到本实例工具进程的环境变量；宿主控制变量禁止覆盖。该映射属于通用接入能力，工具只读取其声明的普通环境变量，不引用 Eval 或 Agent 框架对象。不支持此能力的 Runtime 会明确拒绝该配置，不静默忽略。

生成结果包含工具清单、独立源码审查与独立调用检查记录。验收案例通过 `requirementIds` 关联原业务/运行要求，由实际执行证据逐项判定；未覆盖要求不能导出为完整验收通过。源码审查与调用检查不替代完整业务验证；单环境通过不声称所有框架均已实测。

标准化后的独立调用按声明的输入/输出 JSON Schema 校验，包括对象成功值与字符串错误值的联合类型；不读取远程 Schema。共享 Script 的显式 `{tool, arguments}` 样例会将业务参数 Schema 应用到 `arguments`。外部运行配置尚未提供时，保留 Script 选型并记录未调用及缺少的依赖，不因为需要地址或凭证而强制改为 MCP。无外部依赖的工具仍可独立实测。

平台隔离启动 Python 脚本时显式使用 `-X utf8`，因为 `-I` 会忽略 `PYTHONUTF8` 等环境设置。Windows 的中文及其他 Unicode 输入输出必须按 UTF-8 验证，不能用能解析 JSON 或返回类型正确代替实际文本正确。

Agent 通过 `submit_result` 提交结构化说明，较长方案可先用 `record_result` 分段记录，最后校验完整结果。本地校验器复用构建后的服务端 Schema，并核对连续源码引用。格式或引用不合格时在同一次 Agent 会话中反馈，可用 `correct_result` 仅修正出错字段；引用可按真实文件的行号取得原文，避免重复转写转义字符。不能将分段记录或模型口头确认当作提交成功；服务端仍会重新校验。运行部署需先完成 `build:core`，校验器只读取提交内容，不执行候选代码。

验收证据区分 Skill 说明加载与业务工具执行：`skill_tool`、文件读取和目录查询不代表执行了业务工具；脚本执行需核对实际命令和结果。最终回答使用 SDK 的最终结果，过程文字继续保留在事件记录中。测试数据可按案例提供；验证缺少输入的场景不能附带其他案例的共享输入。

历史候选在同一方案下已被否决时，重新打包相同文件不能覆盖否决结论。比较解包后的完整文件内容，避免 ZIP 时间戳或条目顺序变化被误判为新产物；原文件与原审查记录保持不变。
