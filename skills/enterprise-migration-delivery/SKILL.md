# 企业 Skill 迁移：交付形态

Tool 的实现边界遵循 [企业级 Runtime 无关 Skill 规范第 6 节](../../docs/2.0/skill-specification.md#6-tool-怎样做到与-runtime-无关)：可以解析、校验和使用 Runtime 注入的鉴权信息，不负责建立、选择或切换执行身份。业务入参与运行时依赖分开；声明实际消费的依赖，不统一 Credential 类型，不把凭证获取链路整体搬入工具。以下交付规则不改变这一边界。

凭证与调用上下文由 Runtime 通过声明的独立通道注入，不进入模型可填写的业务参数。HTTP 可以使用请求 header；MCP 和脚本的映射须由具体调用契约明确，不强制使用 header 或 headers 字段。注入按调用隔离，不能依赖共享连接或可变全局状态中的身份。Tool 只读取必要内容，按下游契约构造请求，不无差别透传上下文。阶段处理与传输映射设计见 [迁移中的依赖识别与处理](../../docs/2.0/impl/migration-dependency-handling.md)。

这是**改造阶段**的依据：决定已经做完了（形式由人定、语言由平台算），这里只回答"交付出来的东西要长成什么样才能被平台起起来并调用"。

**判断类规则不在这里。** 合规怎么判、可移植性属于哪个状态、该建议 MCP 还是 Script——那些是检查判断阶段的事，属于另一个技能包。改造阶段拿到的是已经作出的决定，不是要重新做的判断。

## 读哪一份

| 你要做的事 | 读哪一份 |
| --- | --- |
| 服务/脚本的骨架、"能被调用"到底意味着什么、各语言的硬要求 | `references/service-templates.md` |

**这些是骨架，不是必须逐字照抄的模板。** 结构、命名、依赖管理由你决定；不能改的只有那几条硬要求——它们是平台能不能起它、能不能验它的前提。

## 交付必须回答的两件事

1. **怎么起它**：启动命令（argv 数组），需要装依赖或构建就先给一次性准备步骤。平台按它把服务真的起起来。
2. **接口动了哪里**：相对基线改了哪些入参出参，每处都要给理由——迁移必然做适配，有理由的改动是正常的。

## Skill 文档交付

迁移模型负责决定最终文档结构，平台不会在交付后机械合并或拆分文档。优先让用户在一个 `SKILL.md` 中读懂主要流程；只有内容独立、低频且适合按需加载时才放进 `references/`。不要因为源目录存在、Tool 数量或固定行数就创建参考文件。500 行可以帮助判断可读性，但不是硬阈值。

交付前解析最终 `SKILL.md` 的 YAML frontmatter，确认 `name` 与 `description` 是非空字符串；描述中的冒号、引号和换行要用合法的引号或块标量表达，不要留下无法解析的 YAML。

最终 `SKILL.md` 是供模型执行任务的业务工作流，不是工具部署清单。必须保留并澄清源 Skill 中影响决策的内容：

- `description` 说明 Skill 做什么、何时触发，以及容易误用时的边界。
- 正文说明输入来源、工具的业务职责、模型实际承担的调用顺序与分支、返回结果的解释方式。
- 明确失败或缺失时何时停止，禁止编造哪些数据。
- 明确最终输出字段、类型、错误代码及顺序等不可漂移约束。

Skill 指导模型使用工具，不指导模型重做工具。已经由一个工具封装的 HTTP 请求顺序、鉴权、重试、超时、SDK 调用或数值计算，留在工具代码、迁移方案和验收材料中，不展开成模型的执行步骤。输入输出与错误语义仍须清楚；模型确实需要协调多个工具、作业务选择或执行计算时，保留有来源依据的业务规则。按真实执行责任判断，不按标题、HTTP 或公式等关键词机械删除，也不一律把内容移到 references/。

保留业务语义不等于照抄源正文中的实现说明。单个工具已封装查询、校验和计算时，写清一次调用及结果处理，不再列内部请求链、接口路径或计算步骤；仅加“工具内部完成、模型不用执行”的标签不能代替文档职责整理。只有确实影响模型业务选择或输出解释的必要细节才简要保留。

部署地址、Header、环境变量、安装与启动配置放工具工程 README 或配置模板。Skill 只保留模型实际调用所需的说明，例如 Script 调用入口、输入格式与资源读取方式，不把运维配置转成业务参数。不要为每个工具重复“通过 MCP 调用同名工具”之类没有业务含义的句子。若源 Skill 描述不足，应依据已读取的实现补足模型使用所需的契约，而不是抄写内部算法；不能确认的内容明确标为待确认，不得猜测。

业务标识符按用户输入或可信工具结果原样传递。示例不代表规范化规则，不依据示例补字符、改格式或猜值；仅保留源业务契约明确要求的转换，不改变工具 Schema、算法或错误码。

最终文档写入隔离的 `migration-skill/` 目录，并在结果的 `skillDelivery` 中逐项声明源文件和它在 Skill 根目录中的目标路径。清单必须包含目标 `SKILL.md`，并完整列出要交付的文档；未列出的旧文档不会由平台猜测保留。`workspace/` 是运行期数据，不得进入 Skill 文档交付。

文档清单的目标为 `SKILL.md` 或 `references/` 下的 `.md`、`.mdx`、`.txt`；源路径均在 `migration-skill/` 内。工具部署 `README.md` 属于工程文件，放在 `tools[].files`，不再放入 Skill 文档清单。明确复用但没有修改的源码模块、包内资源也必须列入 `tools[].files`；平台按实际字节交付，不要求为了收集文件而改写原实现。

原实现中被本次迁移替代的框架注册、返回包装等代码，可以通过可选的 `skillDelivery.retiredSources: [{path, reason}]` 声明不再交付。使用原上传包的精确相对路径，说明基于实际源码和已确认方案的替代关系。不要在工作区删除原文件，不按名称猜测退役；文档、业务资源、配置及未迁移工具仍需要的共享代码不属于此清单。平台只从新候选中排除，保留原资产并展示删除差异及理由。候选分析和独立方案一致性审查仍需核验行为、依赖和引用，没有因为格式合法而跳过审查。

接口与基线的差异只进报告，不参与通过与否。判通过与否的是**起得来、工具有、调得通**。

## 当前平台交付契约

Script 通过通用 command 执行，不注册为独立业务 Tool，也不支持额外 Runtime 上下文或凭证注入。执行 cwd 是 workspace，Skill 可以在其他目录；脚本使用 Runtime 给出的绝对路径。包内资源基于 __file__ 或 import.meta.url 定位，相对业务文件及产物位于 workspace。不要在交付代码中写死平台部署路径。

业务服务地址、固定超时等 SERVICE_ENV 配置由 MCP 服务从声明的环境变量读取，只在对应子进程启动时提供；工具级 serviceEnvironment 的 key/name 与诊断一致，不写死值、不转成 Header 或业务参数。tools/list 不访问业务接口、不要求真实配置；必需配置缺失时业务调用前明确失败。

MCP 通过每次请求 Header 消费上下文和最终 Credential，业务 Schema 不包含这些隐式依赖；Runtime 负责身份和凭证获取 SDK。交付 JSON 的 runtimeBindings 必须与诊断 key/header 对应，顶层 runtimeToolConfig 确认平台提供的无实际值模板。未知 Provider、类型或企业接入信息不得猜测。平台根据最终包路径生成 Skill 执行指引和包根目录的 runtime-tool-config.template.json；模板的环境变量由执行方提供，不代表实际调用已经通过。

新生成的 Python MCP 服务使用独立包 `fastmcp==2.14.7`，入口导入 `from fastmcp import FastMCP`。通过具名业务函数、类型注解与必要的 Pydantic 约束定义工具，实际发现 Schema 后与基线核对；差异明确记录原因。当前请求的 Header 通过 `fastmcp.server.dependencies.get_http_headers` 读取，不缓存身份，不新增 MCP 鉴权门槛，不将凭证放入函数的业务参数。依赖和启动命令由交付包声明，不依赖平台或 openJiuwen 的安装环境。

## Runtime Harness 边界

本交付步骤只处理 Skill 文档、业务 MCP 和独立 Script。诊断中的 `runtimeCapabilities` 是待核验的原生能力需求，不等于目标 Runtime 一定缺少。业务部分可以先生成，但不能在本步骤生成 Harness 插件或伪造原生能力已经可用；Runtime 适配阶段先核对已登记 Launcher 的完整合同，满足则复用。不满足时补齐 `finance.runtime-build-requirements.v1` YAML，等待 Builder 交付和准入。两种路径都需要实际运行和业务验证，不能仅凭同名工具通过。

外部 Builder 消费该 YAML，构建并返回 Launcher；Eval 负责准入与实际业务验证。ToolBase、ToolResponse、Toolkit、register_tool 等框架注册与返回包装属于迁移适配胶水，应由业务 MCP/Script 的目标框架实现替代，不得误报为 Harness 改造需求。普通包内参考文档阅读也不自动形成新的 Harness 接口。

## 库依赖分类

诊断 SDK 依赖通过 library 区分 STANDARD_LIBRARY、PACKAGE、CUSTOM_SDK、UNKNOWN，并引用真实 import。标准库由平台运行环境清单核对，不能将本地同名模块标为标准库，也不要求用户上传源码。第三方包声明实际发行名和依赖清单路径，引用声明原文；已声明不等于已安装或导入成功。企业自定义 SDK 仍需实际源码或契约。迁移保留第三方包的版本约束，写入交付依赖清单并通过包内环境运行；不安装标准库的同名第三方包，不借用模型工作区全局安装环境。
