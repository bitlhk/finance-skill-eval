# 企业 Skill 迁移：判断依据

这是迁移平台自己的判断依据，不是要求被检查的工程遵守的新文件。

Tool 的职责边界以 [企业级 Runtime 无关 Skill 规范第 6 节](../../docs/2.0/skill-specification.md#6-tool-怎样做到与-runtime-无关)为准：Tool 可以解析、校验和使用鉴权信息，但不建立、选择或切换执行身份。

**改动交付形态的规则不在这里**——服务怎么写、怎么起、怎么被验，属于改造阶段，在另一个技能包 `enterprise-migration-delivery` 里。本技能包只负责**读这个包并给出判断**。

一个源工程读完之后，要回答：**文档是否合规、使用哪些工具、工具的可移植性与建议形式、每个工具的执行链路与实际依赖、哪些缺项需要用户提供**。这些结论共用同一套证据要求。

### 逐工具链路与依赖补齐

沿入口追踪跨文件调用、SDK、接口、配置、数据、资源以及转换和错误分支。节点、类型与依赖引用都要提供真实 path + snippet，不能编造外部服务内部逻辑。记录边界，不执行原版。

依赖区分 AVAILABLE、MISSING、UNKNOWN；已有实现要列出实际读取的 resolvedPaths。稳定 key 由实际实现或注入项确定，不能因变量名相同就共享。references 列出使用该依赖的每个工具和源码证据。

先区分 Tool 代码依赖、Tool 实际消费的运行时依赖，以及 Runtime 建立执行身份的内部实现。运行时数据与凭证只需要识别契约，不要求诊断阶段填写实际值，也不因缺少实际值阻塞迁移。缺代码且影响理解或转换时，才要求补充实现或接口说明。

Tool 实际消费的凭证和隐式调用上下文，应识别为 Runtime 通过独立注入通道提供的依赖，与模型填写的业务参数分开。记录依赖的含义、表示方式和读取位置；不能把整个原 Context 对象搬进工具入参，也不能把仅用于获取凭证的上下文一起声明。HTTP header 是一种传输映射，不要求 MCP 或脚本统一使用 header；具体机制属于各类工具的调用契约。

依赖识别和各阶段处理原则见 [迁移中的依赖识别与处理](../../docs/2.0/impl/migration-dependency-handling.md)，这些流程规则不属于 Skill 标准。

沿 user → auth_sdk → 凭证 → 业务接口的链路寻找 Tool 实际消费的依赖边界；仅用于获取凭证的 user 和身份建立 SDK 不应整体搬入 Tool 声明。auth_sdk 中解析、校验已注入凭证的方法可以保留，建立身份的方法属于 Runtime。不能只按 SDK 名称判断归属。

依赖类型与字段依据源码或类型定义，不统一 Credential 类型。局部字段访问只给 PARTIAL；完整类型定义才可 COMPLETE；未知类型写 null。补充代码材料单独放在 .diagnosis-supplements/，继续读取它们分析。二进制不可读时仍标 UNKNOWN。

缺材料不清空已确认结果，返回部分诊断及明确缺项；无法确认的整体可弃权，但保留已确认部分。测试数据与凭证在测试阶段按 Tool 声明配置，不提供给静态分析模型。

## ① 证据：什么才算数

### 两条路，规则不同

| | 给什么 | 谁定行号 | 对不上会怎样 |
| --- | --- | --- | --- |
| **发现**（合规问题） | `path` + `line` + 原文片段 | **你给**，平台会核对 | 这条发现被丢弃 |
| **分析主张**（工具、输入输出、样例、证据） | `path` + 原文片段，**不要给行号** | **平台按片段算** | 这条主张不成立 |

发现的 `line` 必须落在该文件的行数范围内，且片段能在那一行里逐字找到——**三条缺一条，这条发现就会被平台丢弃**，不是你写得不漂亮，是它落不到源码上。

分析主张反过来：**行号是平台算的，不是你数的**。你只需要抄准原文——在那份文件里能唯一确定那一行就够，一行里的关键半句即可。原文找不到，这条主张就不成立（平台不会退回用你猜的行号）。

**两条路的共同点：先定位，后表述。** 找到一个能对上的位置，再写这条结论。凑不出来的，宁可不写。

### 覆盖率：回答"我漏了什么"

平台有一个确定性的静态扫描器（`run_scanner`），枚举全部文件并报告哪些读不了（二进制、超限），同时给出**工程的文件架构**（目录清单 + 每个文件的角色）。

**它比你自己读文件可靠，因为它回答的是"没看的"，而你只能回答"看到的"。**

- 动手之前先调 `run_scanner`，拿到确定性发现、覆盖率与文件架构；
- 架构就是"这个包由什么组成"的答案，先看它再决定读哪几个文件；
- 覆盖率不全时，在 `coverageGaps` 里**如实列出**漏看的部分；
- **不要**用"我大概扫过了"代替覆盖率声明。

覆盖率不全会导致平台要求人工确认后才能继续生成——这是设计如此，不是报错。

### 弃权

证据不足、或关键文件读不了时，把 `status` 置为 `ABSTAINED`，写清 `reason` 与 `missing`。

**弃权是合法的产出，不是失败。** 编一个看起来对的结论，比诚实弃权有害得多。

## ② 分析：这个 Skill 用到了什么

回答三个问题，**每个答案都要能指到出处**：

1. 这个 Skill **用到了哪些工具**；
2. 每个工具的**输入输出**是什么；
3. **样例**是什么。

产出同时是两样东西：**基线**（迁移保留什么、校验比什么）和**出题的种子**。

### 输入输出从哪读

**优先读 Skill 文档对工具用法的描述**，而不是从实现代码里反推。Skill 文档是业务方写的契约——它说"传什么、回什么、失败了怎么办"，工具就该收什么、回什么。

| 出处 | 强度 |
| --- | --- |
| Skill 文档里对工具用法的描述 | **首选**——这是业务契约 |
| 工具自己声明的 Schema（MCP 的 `inputSchema` / `outputSchema`） | 强——协议强制的自描述 |
| 实现的签名与类型标注 | 次之——`def f(a: str) -> dict` 只给出粗形状 |
| 调用处的参数构造 | 再次——能看出实际传了什么 |

**输入和输出分开报，各自给出处。** 一个来自文档、一个来自签名，是正常的。

### 样例从哪读

样例是**具体的输入/输出实例**，不是形状描述。它可能来自：Skill 文档里的例子；测试文件；实现的默认值、docstring、注释里的示例。

**读不到样例就写 `[]`，不要编。** 编出来的样例会被当成测试数据用——那样测试在测一个虚构的世界。

### 四条不许做的事

1. **不许扫散文里的反引号当工具名。** `SKILL.md` 里出现的 `` `JSON` ``、`` `pyproject.toml` `` 不是工具。工具是"能力"，有实现或至少有用法的明确描述。
2. **不许把注释和字符串里的 SDK 名字当依赖。** 只有真实的 import / 调用 / 继承才算。
3. **不许从函数名猜 Schema。** 名字说明不了输入输出；读不出来就报 `null`。
4. **不许编样例。** 见上。

### 契约读不出来时

某个工具的输入输出**读不出来**时，如实报 `null` 并说明缺什么。**不要**用"看起来像"的形状填上。

读不出来意味着这个工具**没法校验迁移有没有改坏它**——这是要让人知道的结论，不是要藏起来的问题。

## ③ 合规检查：文档符不符合规范

只判断**文档是否符合规范**，不判断 Tool 能不能运行。

| 检查项 | 判据 | 严重度 |
| --- | --- | --- |
| 唯一入口 | 有且仅有一个 `SKILL.md`，大小写准确 | ERROR |
| 入口位置 | 位于 Skill 包根目录，不是嵌套在子目录里 | WARNING |
| `name` | 存在、非空、与所在目录名一致（目录名允许 `skill` 这一通用名） | ERROR / WARNING |
| `description` | 存在、非空、说明**何时使用**（不是复述标题） | ERROR |
| 引用存在 | frontmatter 与正文中以 `` `references/...` ``、`` `scripts/...` ``、`](./...)` 形式引用的文件都必须真实存在 | ERROR |
| 目录卫生 | 除了 `SKILL.md`，顶层只允许 `scripts/`、`references/`、`assets/`。可执行脚本放在 `references/` 或根目录属于待迁移问题，**不阻塞生成** | WARNING |
| 凭据 | 正文或 frontmatter 中不得出现硬编码的密钥、口令、令牌 | ERROR |
| 绝对路径 | 不得出现机器专用绝对路径（如 `C:\Users\...`、`/home/...`） | WARNING |
| 失败处理 | 必须说明信息不足、失败、被拒绝时怎么办 | WARNING |
| Runtime 专用步骤 | 不得把源 Runtime 的安装或注册步骤写进 Skill | WARNING |

### 明确不做的判断

- **不**因为 Tool 是 Java / Python / 其他语言而判 Skill 不合规。
- **不**因为文件多、文档长而判不合规。
- **不**把"缺 Tool 清单"当作错误——平台自己从源码提取，不要求 Skill 提供清单。

### 输出

每条 finding 必须带 `code`、`severity`、`path`、`line`、`message`、`suggestion`。`line` 的规则见第 ① 节。

## ④ 可移植性：每个 Tool 属于哪个状态

**状态是静态判断，不是验证结果**——它不代表"已经验证通过"。

| 状态 | 判定条件 |
| --- | --- |
| `PORTABLE_MCP` | 有证据表明它已经是可以独立启动、独立调用的 MCP Tool：有 Server 入口、有工具注册、有可读的输入 Schema |
| `PORTABLE_SCRIPT` | 有证据表明它已经是可以独立运行的命令行 Tool：有入口文件、从标准输入读 JSON、向标准输出写 JSON |
| `RUNTIME_BOUND` | 业务实现存在，但调用方式依赖源 Runtime：import 了 Runtime SDK、从 Runtime 取 Context / Session、依赖 Runtime 的注册或资源注入 |
| `INCOMPLETE` | 业务实现、输入输出或必要依赖不完整——缺入口、缺实现、缺依赖声明 |
| `UNSUPPORTED` | 当前平台不能自动处理这种实现（例如依赖了无法替代的外部系统） |
| `UNKNOWN` | 证据不足，或检查未完成 |

### 四条例外（重要）

1. **`UNKNOWN` 不得提升为可移植。** 拿不准就是 `UNKNOWN`，不要因为"看起来像"就写成 `PORTABLE_*`。
2. **注释和字符串里的 SDK 名字不算依赖。** 只有真实的 import / 调用 / 继承才算。
3. **函数名不能单独证明输入输出 Schema。** Schema 必须从源码的类型标注、参数解构、MCP 自描述里读出来；读不出来就是 `null`，不要编。
4. **能不能真正运行由后续技术验证决定**，不由这里的静态判断决定。所以这里不做"已验证通过"的表述。

### 发现顺序（先强证据，后弱证据）

1. MCP 的 `tools/list` 或可静态读取的 MCP 声明；
2. `SKILL.md` 里明确提到的 Tool；
3. Runtime SDK 的 Tool 注册（装饰器、注册函数、注解）；
4. 命令行入口、函数定义；
5. 只是被提到、没有任何实现佐证的名称——**作为提示，不认定为 Tool**。

## ⑤ 形式建议：MCP 还是 Script

给出**建议形式**与**建议语言**。建议供人参考，**不代替人决定**。

涉及企业鉴权、动态凭证或敏感运行时上下文时，优先建议 MCP，并提供源码依据与原因；不能仅因任务一次性或在本机执行就推荐 Script。这个建议不构成 Script 的合规禁令，也不意味着 MCP 自动解决鉴权。已有 Script 如具备安全注入、按调用隔离和执行后清理机制，可以保留；用户选择 Script 时应说明这些接入要求，避免通过命令行参数传递凭证。

| 现状 | 建议形式 | 理由 |
| --- | --- | --- |
| 已经是合规的 MCP Tool | `MCP` | 保留原实现，不因语言不同而重写 |
| 已经符合独立 JSON Script 协议，且所需敏感依赖具备安全注入机制 | `SCRIPT` | 原样复用 |
| 依赖企业鉴权、动态凭证或敏感运行时上下文，且尚未具备安全的 Script 接入机制 | `MCP` | 优先服务化接入凭证注入、访问控制和审计；仍需明确具体契约 |
| `RUNTIME_BOUND` 且是**被多方调用**的服务型能力 | `MCP` | 需要被不同系统调用，且能共用同一个服务 |
| `RUNTIME_BOUND` 且是**一次性、本机、单入口**的任务，不存在上述敏感依赖接入问题 | `SCRIPT` | 安装依赖和命令行调试更省事 |
| 有大量数据/文本处理、依赖丰富生态库，且满足所需敏感依赖的接入要求 | `SCRIPT` | 可以同语言复用，减少重写的代价与风险 |
| `UNSUPPORTED` | 不给建议 | 交给人工判断 |

### Runtime Harness 能力归属

判断工具职责，不按名称猜归属。Runtime 提供的通用文件读取、搜索、命令执行等底层能力属于 Harness，不建议绑定 Skill，不迁移实现。带企业权限、业务规则或内部服务调用的同名工具仍按业务工具分析；混合工具保留业务部分。

将已确认的 Harness 能力单独记录到 `runtimeCapabilities`，引用真实原文并说明参数、返回值、路径、权限及错误约定（不明项明确列出）。不放入业务 `tools`、`dependencyAnalysis.dependencies`、`dependencyAnalysis.chains` 或缺失依赖补充清单；Harness 自身使用的标准库、SDK、配置和资源也不进入业务迁移依赖图。一旦存在真正的 Harness 能力需求，当前迁移在诊断阶段停止并输出 `finance.runtime-build-requirements.v1` YAML，等待未来 Runtime Builder 返回可登记的 Runtime 接口；不得生成候选插件或进入测试。未提供目标能力清单时不猜映射，也不宣称能力已可用。ToolBase、ToolResponse、Toolkit、register_tool 等注册与返回包装只是框架胶水，不属于 Harness 能力需求，仍按普通工具迁移处理。

### 语言建议

语言**不由你判断**。你只给形式建议，实现语言由平台按下面这条固定判据算出。

判据是**同语言优先**——跨语言重写是这个平台风险最高的动作：

1. 源语言已经是该形式的目标语言 → 用源语言；
2. 否则按生态最接近的选；
3. 看不出生态倾向 → `MCP` 用 `java`，`SCRIPT` 用 `python`。

源语言不在平台支持范围内 → `UNSUPPORTED`，**不给建议**。那需要人工处理，不是迁移。

**不要因为"Java 更规范"就建议 Java。** 跨语言重写会损失保真度，代价也远高于同语言迁移。

### 授权与技术的边界（必须分清）

| 问题 | 谁决定 | 为什么 |
| --- | --- | --- |
| 这个 Tool 的**业务行为允不允许脱离原系统运行** | **人** | 合规与风控问题，平台没有依据可判断 |
| 选 MCP 还是 Script | 人（参考平台建议） | 影响部署形态，属于人的取舍 |
| 用哪种语言实现 | 平台建议，人可覆盖 | 是工程可行性判断 |
| 这个 Tool 技术上能不能迁 | 平台 | 有证据可依 |

**不要把"技术上行不行"包装成"业务上允不允许"。** 也**不要**因为技术上可行就替人做授权决定。

## 服务部署配置

沿源码链路区分静态部署配置与按调用的身份上下文。业务地址、固定超时等声明 CONFIG + RUNTIME + INJECT，binding.kind=SERVICE_ENV，name 是明确的环境变量名，schema 按源码消费类型声明，并提供对应证据。这是迁移接收契约，不要求原代码已有环境变量。实际值由用户在诊断页补充，缺少实际值不阻塞静态诊断或生成。不得将业务地址声明成请求 Header、身份字段或业务参数；凭证获取仍由 Runtime Provider 负责。

## 库依赖分类

诊断 SDK 依赖通过 library 区分 STANDARD_LIBRARY、PACKAGE、CUSTOM_SDK、UNKNOWN，并引用真实 import。标准库由平台运行环境清单核对，不能将本地同名模块标为标准库，也不要求用户上传源码。第三方包声明实际发行名和依赖清单路径，引用声明原文；已声明不等于已安装或导入成功。企业自定义 SDK 仍需实际源码或契约。迁移保留第三方包的版本约束，写入交付依赖清单并通过包内环境运行；不安装标准库的同名第三方包，不借用模型工作区全局安装环境。
