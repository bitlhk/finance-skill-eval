# 迁移建议规则

给出**建议形式**与**建议语言**。建议供人参考，**不代替人决定**。

## 形式建议：MCP 还是 Script

| 现状 | 建议形式 | 理由 |
| --- | --- | --- |
| 已经是合规的 MCP Tool | `MCP` | 保留原实现，不因语言不同而重写 |
| 已经符合独立 JSON Script 协议 | `SCRIPT` | 原样复用 |
| `RUNTIME_BOUND` 且是**被多方调用**的服务型能力 | `MCP` | 需要被不同系统调用，且能共用同一个服务 |
| `RUNTIME_BOUND` 且是**一次性、本机、单入口**的任务 | `SCRIPT` | 安装依赖和命令行调试更省事 |
| 有大量数据/文本处理、依赖丰富生态库 | `SCRIPT` | 换成 MCP 往往要求重写成另一种语言，代价与风险都高 |
| `UNSUPPORTED` | 不给建议 | 交给人工判断 |

## 语言建议

| 形式 | 建议语言 |
| --- | --- |
| `SCRIPT` | `python`；纯 shell 胶水或已有 Node 实现用 `node` |
| `MCP` | **源 Tool 的语言**；源语言不适用时，用与它最接近、且有成熟 MCP SDK 的语言 |

**不要因为"Java 更规范"就建议 Java。** 跨语言重写会损失保真度，代价也远高于同语言迁移。

## 授权与技术的边界（必须分清）

| 问题 | 谁决定 | 为什么 |
| --- | --- | --- |
| 这个 Tool 的**业务行为允不允许脱离原系统运行** | **人** | 合规与风控问题，平台没有依据可判断 |
| 选 MCP 还是 Script | 人（参考平台建议） | 影响部署形态，属于人的取舍 |
| 用哪种语言实现 | 平台建议，人可覆盖 | 是工程可行性判断 |
| 这个 Tool 技术上能不能迁 | 平台 | 有证据可依 |

**不要把"技术上行不行"包装成"业务上允不允许"。** 也**不要**因为技术上可行就替人做授权决定。
