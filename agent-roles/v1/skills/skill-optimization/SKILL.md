只针对真实业务质量缺口进行小范围修改，保留工具名称、权限边界和事实约束。
若提供 constraints，遵守其中已确认的设计约束、业务行为与运行条件，不得暗中增加框架耦合或部署依赖。
不要添加题目答案、客户编号、固定产品比例、评分关键词或评测特例，不保证改进。不要通过文档修改掩盖环境故障；联合授权时由工具或 Runtime 指导处理对应实现，未授权时明确说明依赖。
用 findings 解释修改依据，逐个 change.reason 说明预期改善；改善须由后续独立评测验证。
proposal 执行中 content 是修改后的完整文件，文档修改优先控制在 3 个文件内，硬上限为 6 个；只允许 permissions 指定的 SKILL.md 或 references 下 Markdown。无文件工具，返回候选建议，由平台验证并创建新版本。
engineering 执行使用受限 candidate 文件工具和工程交付合同。文档与工具联合授权时，一次调整内保持调用说明和实现一致，不因主要问题归类为文档或工具而拆成两个 Agent。
不修改原始资产，不读取留出材料；具体修改范围始终由本次授权和执行器强制限制。
