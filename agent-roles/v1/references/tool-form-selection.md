# 工具形式选型

先核实已有实现、调用者、部署环境、身份边界与实际需求，再比较 MCP、CLI、Script。它们不是互斥的业务分类：Script 可调用 CLI/API，MCP 可适配已有 CLI；每增加一层必须说明收益，不能为了形式重写业务。

- MCP：工具发现和参数 Schema、多个客户端复用、集中提供工具/资源等协议能力有明确价值时考虑。远程托管、认证授权、租户隔离、审计、限流、版本治理需要具体实现和运维证据，不能由“MCP”三个字推断已具备。也可能通过本地 stdio 使用，不等于必须开放公网服务。
- CLI：已有成熟命令，或开发者、Agent、CI 需要共用稳定操作入口时考虑。核实安装与版本、平台兼容、子命令/参数、非交互模式、机器可读输出、退出码、日志分离、超时及身份来源。复用成熟命令通常比重新实现其 API 更稳妥，但不能假设命令已经安装。读操作不强求 dry-run；写操作需定义预览/确认、幂等和重试边界，不使用 --yes 绕过业务确认。
- Script：随 Skill 分发的局部逻辑、文件处理、胶水代码、试验或低频任务通常易于落地。说明参数、结果、错误、依赖锁定、cwd、资源路径和执行限制。复杂确定性分支可写入脚本，但不能把 Skill 应由 Agent 决策的流程机械固化。长期跨团队复用时需比较维护与分发成本，不能因“改动最少”就默认最优。

比较时覆盖：现有能力能否保留；真实调用者和部署限制；发现与接口稳定性；依赖分发和平台兼容；身份、凭据、权限和状态隔离；过程证据；调用开销；改造、部署及长期维护成本。不要虚构用户规模、延迟、费用和工时。缺少影响结论的事实时说明条件，提出具体待确认问题。

方案给出选中项、其他两项的收益/代价与不选理由。允许不同工具采用不同形式，考虑共享部署和公共依赖；不能因为连续调用就合并工具。先保持业务语义，再将有依据的性能或效果优化作为明确的调整建议。

Review 独立核对选型依据是否来自源码、用户目标或已验证环境。已确认方案也可能存在错误；不合理的选型应列入问题并要求修订，不能以“实现符合方案”证明方案合理。源码审查、协议检查、实际调用和业务效果分别给结论。
